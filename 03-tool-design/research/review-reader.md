диаграммы не наезжают друг на друга и не обрезаны. Отдельно прогнан `grep` по всему тексту на

Общая оценка не изменилась: глава читается как «глава», не как конспект. Структура не анкетная,
первые предложения разделов не образуют пересказ, разделов-воды нет, числа почти везде сверены и
совпадают. Главная проблема — как и в прошлый раз, происхождение части цитат с Hacker News, но
теперь это подтверждено не только отсутствием в заметках, а прямым открытием первоисточника.

## Critical

### 1. Часть цитат с Hacker News присвоена не тем людям или выдумана; прямая проверка первоисточника это подтверждает

**Место:** `#tool-search` (цитата приписана jmward01), `#code-mode` (цитата olliem36),
`#bash-cli` (цитаты redhale/beoberha, mrubon, sonofaragorn, 5ersi, Aldipower, erikus).

**Что я сделал.** Для каждой из девяти цитат с именем и/или постоянной ссылкой на конкретный
комментарий я открыл этот комментарий напрямую (`WebFetch` на `news.ycombinator.com/item?id=…`) и
сравнил автора и текст с тем, что написано в главе. Результат разный по каждой цитате:

**Подтверждено дословно (не находка, для протокола):**
- `#code-mode`, olliem36, `item?id=46044877` — комментарий существует, автор действительно
  olliem36, и приведённый в главе фрагмент «If something goes wrong halfway through the code
  execution of multiple 'tools' using Programmatic Tool Calling, it's significantly more complex
  for the AI model to fix that code and try again compared to a single tool usage — you're in
  trouble, especially if APIs/tools are not idempotent» — точная подстрока настоящего комментария.
- `#bash-cli`, mrubon — фраза «I find clis or calling apis directly to be waaay cheaper and
  faster» — точное начало настоящего комментария mrubon в треде `item?id=49548600`.
- `#bash-cli`, redhale/beoberha — оба ника реальные участники того же обсуждения
  (`item?id=45822258` и его ветка), и ответ beoberha по смыслу и почти дословно совпадает: «MCP
  server is a one stop shop for discovering "tools"» ≈ «a one stop shop for discovering „tools"»
  в главе. Сам ли комментарий redhale «My mantra is: just use CLI tools…» лежит ровно под этим id,
  проверить однозначно не удалось (прямой запрос к этому id вернул другую реплику redhale в той же
  ветке) — считаю это подтверждённым по контексту, но не по конкретному id.

**Не подтверждено, притом что тема того же треда проверена:**
- `#tool-search`, jmward01, `item?id=46039238` — **комментарий по этой ссылке принадлежит не
  jmward01, а пользователю vendiddy, и текст другой**: «Giving the AI an actual programming
  language (functions + objects) genuinely does seem like a good alternative to the MCP mess we
  have right now». Ни автор, ни цитата «Good context engineering leaves the tools you will
  need…», приписанная в главе jmward01, по этой ссылке не существуют. Это не пропуск в заметках
  (как думал предыдущий проход рецензии) — это неверная атрибуция, проверяемая прямо по
  первоисточнику.
- `#bash-cli`, Aldipower — открытый комментарий Aldipower в том же треде (`item?id=49548600`)
  говорит: «We use MCP in production since March 26 for user-facing endurance sports analytics and
  planning». Про ChatGPT, Claude, Grok, Perplexity и Mistral без шелла там ни слова.
- `#bash-cli`, erikus — открытый комментарий erikus в том же треде говорит: «I use MCP for a voice
  assistant as well. I got a Pebble Index 01 ring and it has support…». Про «I don't want to give
  the agent a shell, and a narrower MCP interface is a great fit» ни слова.
- `#bash-cli`, 5ersi — открытый комментарий 5ersi говорит: «MCPs are diminishing in value a bit,
  because AI Agents are getting smarter about using API/CLIs». Фраза про `gh`, GitHub MCP и «across
  five different (legacy) systems», приписанная в главе 5ersi, дословно совпадает с анонимным
  фрагментом из `gaps.md` (`[G47]`) — то есть содержание реально есть где-то в этом 201-комментарийном
  треде, но что его написал именно 5ersi, ни заметки, ни точечный запрос к его профилю не
  подтверждают (тред большой, у пользователя может быть несколько реплик, но и Aldipower, и erikus
  дают ровно один результат на запрос, и оба раза он расходится с главой).

Для двух реплик из пяти в тесте на «Ask HN» (sonofaragorn — по смыслу совпадает, mrubon — совпадает
дословно) атрибуция подтвердилась. Для двух (Aldipower, erikus) — прямо опровергнута открытым
комментарием под их именем. Для одной (5ersi) содержание реально в треде есть, но не по имени.
Итого: минимум одна цитата в главе (jmward01) — гарантированно неверная атрибуция несуществующей
под этим id цитаты, и ещё две (Aldipower, erikus) — приписывают людям слова, которых их открытые
комментарии не подтверждают.

**Почему это критично.** `AUTHORING.md` §4 прямо запрещает выдумывать цитаты и требует, чтобы
каждая нетривиальная цитата была в заметках; `research/field.md` и `research/gaps.md` дают
содержание этих цитат только обезличенно (`[S9]`, `[G47]`), без имён — то есть ни ники, ни
конкретные id комментариев не восстанавливаются даже из собственных материалов автора, что уже
было находкой прошлого прохода. Теперь это подтверждено сильнее: часть атрибуций прямо
противоречит содержимому по указанной ссылке. Читатель книги получает вымышленное «полевое
доказательство» (конкретное имя, конкретная дата, конкретная постоянная ссылка), поданное как
настоящее, — ровно тот вид ошибки, для которого в чеклиста критичности есть формулировка
«научит читателя неправильному».

**Что сделать.**
1. `jmward01`/`item?id=46039238` — убрать эту атрибуцию и ссылку немедленно, это точно неверно.
   Либо найти настоящего автора фразы «Good context engineering leaves the tools you will need…»
   в треде `item?id=46038047` и процитировать с верной ссылкой, либо оставить мысль без имени
   («на Hacker News в этом же треде звучало…», как уже сделано в паре мест главы).
2. `Aldipower` и `erikus` — то же самое: либо найти в треде `item?id=49548600` комментарии,
   которые действительно говорят то, что им приписано, и сослаться на них персонально, либо снять
   персональную атрибуцию.
3. `5ersi` — либо найти среди его комментариев именно тот, что говорит про `gh` и «five different
   (legacy) systems», и сослаться на него отдельным id, либо привести фразу без имени, как уже
   сделано с частью материала того же треда (например, фраза про «across five different (legacy)

4. `redhale`/`item?id=45822258` — свериться ещё раз, что «My mantra is…» действительно лежит под

5. `jmward01`, `olliem36`, `mrubon` показывают, что при аккуратной проверке цитаты в этой главе в

## Major

### 2. Единственный найденный в главе бенчмарк «GIA» — вероятно, опечатка первоисточника, которую глава не поясняет

**Место:** `#code-mode`, «Точность на внутреннем тесте поиска знаний выросла с 25,6 до 28,5%, на
бенчмарке GIA — с 46,5 до 51,2%».

**Проверка.** Я открыл первоисточник этого абзаца (`anthropic.com/engineering/advanced-tool-use`,
src-13) напрямую. Anthropic там действительно пишет «GIA benchmarks» — но ссылка на этих словах
ведёт на `arxiv.org/abs/2311.12983`, а это статья «GAIA: a benchmark for General AI Assistants».
То есть сам первоисточник, судя по всему, содержит опечатку (GIA вместо GAIA) в тексте статьи,
и глава эту опечатку воспроизводит один в один, без пояснения. Это не выдумка автора главы —
заметки (`spec.md`, `practice.md`, `field.md`) тоже везде пишут «GIA» — но для читателя, который
попробует найти «бенчмарк GIA», поиск ничего не даст: реальное название — GAIA.

**Что сделать.** Добавить в скобках или сноской реальное название и ссылку: «на бенчмарке GIA
(вероятно, опечатка источника; имеется в виду GAIA, arXiv:2311.12983)». Одно предложение снимает
риск, что внимательный читатель потратит время на бесплодный поиск.

Крупных дыр помимо этих двух находок не нашёл: числа на рис. 3.1, 3.3, 3.8, 3.9 (проверены вручную
построчно — делятся и складываются верно), даты моделей и версий (`code_execution_20260120`,
отмена принудительного `tool_choice` на Opus 5.5/Sonnet 5.5/Fable 5.1/Mythos 5.1, ревизии MCP
2025-06-18→2025-11-25→2026-07-28, бюджеты строгой схемы 20/24/16) совпадают с `gaps.md` дословно, в
том числе там, где заметки прямо предупреждают о частой ошибке («strict несовместим с
параллельными вызовами» — глава верно даёт уточнённую версию про дообученные модели). Ни одного
примера кода без пометки «Набросок», который не исполнялся бы автором, не нашёл.

## Minor

### 3. `resultType` появляется в примере кода один раз и нигде не объясняется

**Место:** `#errors`, блок кода «Ошибка выполнения, пример из спецификации MCP 2026-07-28»:
```json
"result": { "resultType": "complete", "content": [...], "isError": true }
```
**Проблема.** Поле `resultType` встречается в файле ровно один раз (проверено `grep`), и текст под
примером комментирует только `isError` и текст ошибки. Внимательный бэкендер, который до этого
читал про протокол без сессий и `tools/list` без состояния, зацепится взглядом за незнакомое
обязательное поле в JSON-RPC результате и не получит ответа — ни что значит `complete`, ни какое
у поля другое значение. Небольшая потеря нити, явно вынесенная в главу 5 про сам протокол, но без
единого слова-мостика в этой главе.

**Что сделать.** Либо убрать `resultType` из примера, раз в тексте о нём ни слова, либо добавить
одну фразу о том, что это обязательное поле результата в этой ревизии, с явной отсылкой к главе 5.

### 4. Два пункта чеклиста — не «сделал», а «могу объяснить»

**Место:** `#checklist`: «Могу объяснить, что гарантирует `strict` у Claude и у OpenAI и какие
проверки… остаются на сервере» и «Могу обосновать выбор между CLI и MCP-сервером для внутреннего
инструмента своего бэкенда».

**Проблема.** `AUTHORING.md` §5 даёт чеклисту образец: каждый пункт проверяется делом («могу
написать…», «умею найти в логе…», «поднимал…»). Остальные 11 из 13 пунктов главы — действия
(«писал», «нашёл», «переводил», «делал»), и это два единственных исключения, которые проверяются
собеседованием, а не делом.

**Что сделать.** Переформулировать в действие, например: «Переписывал строгую Claude-схему так,
чтобы избавиться от `minimum`/`maxLength`, и перенёс проверку диапазона на сервер» вместо «могу
объяснить»; «Выбирал между CLI и MCP-сервером для конкретного внутреннего инструмента и записал
почему» вместо «могу обосновать».
