MCP: Model Context Protocol

Сервер на Python SDK mcp 2.2.0 говорит на одном адресе двумя протоколами. Пришли ему initialize, как учат туториалы 2025 года, и получишь заголовок mcp-session-id и поток SSE. Пришли запрос ревизии 2026-07-28 — вернётся обычный JSON без всякой сессии. Почти всё, что написано про MCP, описывает первый вариант, а Claude Code, ChatGPT и SDK летом 2026 года начали переезжать на второй.

Хост, клиент, сервер

Участников трое, и спецификация называет их точно4. Хост — приложение с моделью: Claude Code, Cursor, ChatGPT. Внутри хоста живут клиенты, по одному на подключённый сервер. Клиент держит связь, добавляет к запросам версию и возможности, разбирает ответы. Сервер отдаёт инструменты, ресурсы и промпты и про модель не знает ничего. В спецификации это записано как принцип проектирования: сервер «should not be able to read the whole conversation, nor "see into" other servers». Разговор целиком видит только хост, и только хост решает, что из ответа сервера попадёт в контекст.

Поэтому сервер не решает, как модель увидит его инструменты. Claude Code обрезает описание тула до 2048 символов1, ChatGPT просит уложить главное из инструкций сервера в 5125, и каждый хост сам решает, грузить описания сразу или по поиску. Сервер пишут один раз, а читают его разные хосты по-разному.

Ради «один раз» протокол и появился. Anthropic, объявляя MCP 25 ноября 2024 года, описала проблему так: «every new data source requires its own custom implementation»6. Если N приложений с моделью хотят достать до M источников данных, без общего протокола это N×M интеграций, с протоколом — N клиентов и M серверов. Насколько «один раз» правда, зависит от того, какую часть протокола поддерживает каждый хост, и в разделе про клиентов видно, что части эти разные.

Сообщения и способ их доставки в MCP разделены. Один и тот же tools/call ходит по stdin и stdout локального подпроцесса или по HTTP к удалённому серверу; от транспорта зависят кадрирование, авторизация и то, как сервер держит нагрузку.

Рукопожатие, которого больше нет

В Manufact, которая делает библиотеку mcp-use и облако для MCP-серверов, после выхода ревизии 2026-07-28 переписали SDK с нуля и объяснили зачем: «Behind a load balancer, the session tied a client to one replica. That led to sticky routing, shared session storage, and gateways that had to understand more of the protocol than an HTTP gateway should need to know»7. Сессия привязывала клиента к одной реплике, отсюда липкая маршрутизация, общее хранилище сессий и шлюзы, вынужденные понимать протокол. А выкатка новой версии, по их же словам, «could also kill the process holding a client session and force the client to start over»: убивала процесс с сессией, и клиент начинал заново.

Сервер отвечал своей версией, возможностями и serverInfo, клиент подтверждал уведомлением notifications/initialized, и дальше обе стороны пользовались только тем, что заявили в начале. По HTTP к этому добавлялась сессия. Правила из ревизии 2025-11-258: сервер «MAY assign a session ID at initialization time», кладёт его в заголовок MCP-Session-Id ответа на initialize, и клиент обязан приложить этот заголовок ко всем следующим запросам. Сервер вправе закончить сессию когда угодно, после чего отвечает 404 Not Found, а клиент, получив 404, «MUST start a new session by sending a new InitializeRequest».

Ревизия 2026-07-28 убрала и рукопожатие, и сессии. Первые два пункта её списка изменений3: «Make MCP stateless: remove the initialize/notifications/initialized handshake. Every request now carries its protocol version and client capabilities in _meta» и «Remove protocol-level sessions and the Mcp-Session-Id header». Цель мейнтейнеры сформулировали в блоге к релизу: «Any request can now land on any server instance behind a plain round-robin load balancer without needing shared storage»9.

Заголовки для тех, кто не читает тело

Чтобы шлюз мог маршрутизировать запросы без разбора JSON, ревизия 2026-07-28 сделала обязательными заголовки Mcp-Method и Mcp-Name2. Параметр тула можно тоже вынести в заголовок: если в inputSchema у поля стоит "x-mcp-header": "Region", клиент добавит к запросу Mcp-Param-Region: us-west111. Секреты так помечать нельзя, заголовки видят все посредники по пути.

Сервер обязан сверить заголовки с телом и при расхождении вернуть 400 с кодом -32020 (HeaderMismatch). Иначе шлюз пропустит запрос по безобидному Mcp-Name, а сервер выполнит то, что написано в теле. Демо-сервер так и сделал. В заголовке стояло одно имя тула, в теле другое:

Тот же демо-сервер открыл сессию по initialize ревизии 2025-11-25, получил в ней Mcp-Name: delete_orders при find_orders в теле и ответил 200 с заказами: в первой эпохе заголовков Mcp-* не было, и сверять их сервер не обязан. Поэтому спецификация просит шлюз, который решает что-то по этим заголовкам, отклонять запросы без MCP-Protocol-Version или с версией старше 2026-07-282. Не-ASCII значения едут в заголовках как =?base64?…?= и сравниваются с телом после декодирования.

На сервере без аутентификации хендл фактически становится bearer-токеном, поэтому его генерируют с достаточной энтропией, например UUIDv4, и дают ему ограниченный срок жизни. Срок стоит написать в описании тула, чтобы модель его видела. А вызов с просроченным хендлом должен вернуть ошибку исполнения тула, из которой модель поймёт, что корзину надо создать заново.

По списку изменений 2026-07-28 ответы tools/list, resources/list и prompts/list больше не зависят от соединения3. Что бывает, когда хендлы не привязаны к пользователю, видно по уязвимостям в разделе о безопасности.

Как клиент угадывает эпоху сервера

Серверы обеих эпох ещё долго будут работать бок о бок, и клиенту, который хочет говорить со всеми, нужна процедура определения. Для HTTP спецификация описывает её так2: отправить запрос новой эпохи и смотреть не только на статус, но и на тело. Сервер новой эпохи отвечает на ошибки своим JSON-RPC-телом, старый такого тела не знает. Сервер новой эпохи, получив запрос первой эпохи, отвечает на GET и DELETE кодом 405 и игнорирует Mcp-Session-Id, не создавая и не возвращая его. По stdio клиент может начать с server/discover.

stdio, Streamable HTTP и то, что осталось от SSE

Самая частая поломка самодельного stdio-сервера — лишний print(). Правило спецификации короткое: «The server MUST NOT write anything to its stdout that is not a valid MCP message»13. Отладочный print("debug:", rows) в теле тула сервера заказов на mcp 2.2.0 положил строку debug: [(1003, 'shipped', 9900, '2026-09-21')] прямо в stdout, в поток, где клиент ждёт только JSON-RPC. Что клиент сделает со строкой, которая не разбирается, спецификация не говорит: может пропустить, может закрыть соединение. Логи пиши в stderr: logging с stream=sys.stderr или print(..., file=sys.stderr). Stderr клиент вправе собирать, пересылать или игнорировать, и считать его признаком ошибки он не должен.

Остальное в stdio просто. Клиент запускает сервер подпроцессом, пишет ему в stdin по одному сообщению JSON-RPC на строку и читает ответы из stdout. Переводов строки внутри сообщения быть не должно. Завершает работу клиент: закрывает stdin и гасит процесс. Авторизации в stdio нет, спецификация просит такие серверы не реализовывать OAuth, а брать секреты из окружения14. В Claude Code это флаг --env у claude mcp add, а в окружение сервера Claude Code ещё кладёт CLAUDE_PROJECT_DIR с корнем проекта1.

Streamable HTTP в новой эпохе

Удалённый транспорт называется Streamable HTTP, он появился в ревизии 2025-03-26 и в 2026-07-28 заметно упростился2. У сервера один эндпоинт, например https://example.com/mcp. Каждое сообщение клиента — отдельный POST. На запрос сервер отвечает либо одним JSON-объектом, либо потоком SSE, который относится только к этому запросу: в нём едут уведомления о прогрессе и в конце сам ответ. Слушающего GET-потока больше нет, демо-сервер на GET ответил 405 Method Not Allowed. Нет и возобновления потока по Last-Event-ID: если поток оборвался, запрос пропал, и клиент отправляет его заново с новым id. Поэтому инструменты с побочными эффектами стоит делать идемпотентными, иначе повтор после обрыва спишет деньги дважды.

У обрыва есть и вторая сторона: закрытие потока ответа сервер обязан считать отменой запроса2. Уведомления notifications/cancelled по HTTP больше не шлют, оно осталось для stdio, где закрывать нечего15. Значит, таймаут балансировщика или клиента (у Claude Code пять минут для удалённых серверов) обрывает тул посередине. Запись, которую нельзя оставить наполовину, делай в транзакции, а долгую работу выноси в задачи, о них ниже. Прогресс по-прежнему есть: клиент кладёт progressToken в _meta запроса, и сервер шлёт notifications/progress с растущим progress в поток этого же запроса16. Клиент может продлевать по ним таймаут, но максимальный держит всегда.

Уведомления, не привязанные к запросу («список тулов поменялся», «ресурс обновился»), теперь приходят по подписке. Клиент открывает долгий запрос subscriptions/listen и перечисляет, что хочет получать3:

Первым сообщением сервер присылает notifications/subscriptions/acknowledged с тем подмножеством, которое готов выполнять, и дальше помечает каждое уведомление в этом потоке полем io.modelcontextprotocol/subscriptionId, равным id исходного запроса. Посылать типы, о которых клиент не просил, сервер не вправе. Поток оборвался — подписка кончилась, и никакого состояния подписок сервер между переподключениями не хранит. Чтобы посредник не закрыл такой поток в тихий час, сервер время от времени шлёт в него строку-комментарий SSE, начинающуюся с :. И любой поток SSE стоит отдавать с заголовком X-Accel-Buffering: no, иначе nginx копит события у себя2.

Локальный HTTP-сервер доступен любому сайту, который открыт в браузере на той же машине, через DNS rebinding. Спецификация требует проверять заголовок Origin и отвечать 403 на чужой, а слушать советует только 127.0.0.1, не 0.0.0.08. Отладочный сервер на всех интерфейсах в офисной сети — открытая дверь.

Первый удалённый транспорт из ревизии 2024-11-05 держал запросы и ответы на двух разных эндпоинтах, как на схеме ниже. В 2025-03-26 его заменил Streamable HTTP, но серверов на старом транспорте много: в документации Claude Code до сих пор есть пример claude mcp add --transport sse asana https://mcp.asana.com/sse1. Выбор обычно делается сам. Сервер к локальным файлам, git или базе на твоей машине — stdio: без сети, без OAuth, секреты в окружении. Сервер к внутреннему сервису компании, которым будут пользоваться коллеги, — Streamable HTTP: отдельный деплой, токен на пользователя, аудит на стороне сервера. Промежуточный вариант, когда stdio-сервер ходит в корпоративный API с личным токеном из переменной окружения, работает, но это тот самый токен в открытом виде на ноутбуке, от которого OAuth и должен был избавить.

Шесть примитивов, из которых работают четыре

The spec describes Resources, Prompts, Tools, and Elicitation. In practice, I believe Tools represent 95%+ of what people actually use MCP for.
— Саймон Уиллисон, Hacker News, 21 сентября 2026

Широко используемых ресурсов и промптов Уиллисон, по его словам, не видел, а реализованного elicitation не видел ни разу. Часть лишнего ревизия 2026-07-28 уже убрала.

Спецификация делит серверные примитивы по тому, кто решает, когда ими пользоваться19. Инструменты вызывает модель. Ресурсы подкладывает в контекст приложение. Промпты выбирает пользователь.

Инструменты

Описание тула — имя, человекочитаемый title, description, JSON Schema входа и, по желанию, схема выхода. Так выглядит ответ на tools/list в спецификации 2026-07-28:

Результат вызова бывает двух видов, и сервер заказов вернул оба сразу. В content лежат блоки для модели: текст, картинка, звук, ссылка на ресурс или встроенный ресурс. В structuredContent — любой JSON, который обязан соответствовать outputSchema, если та объявлена. Для совместимости спецификация просит дублировать структурированный результат текстом, так и сделал SDK. structuredContent — это данные от сервера, к «structured outputs» модели, генерации по схеме, он отношения не имеет.

Ошибок тоже две. Ошибка протокола — неизвестный тул, запрос не по схеме — приходит как ошибка JSON-RPC с кодом вроде -32602, и модели она мало что даёт. Ошибка исполнения приходит обычным результатом с isError: true, клиент должен показать её модели, чтобы та исправилась. Когда серверу заказов передали "status": "lost", он ответил результатом с isError: true и текстом от pydantic: «Input should be 'paid', 'shipped' or 'refunded'». Модель по такому тексту исправит аргумент со второй попытки. Как писать такие ошибки, чтобы они работали инструкцией, — в главе 3.

Аннотации readOnlyHint, destructiveHint, idempotentHint и openWorldHint появились в 2025-03-26, чтобы хост мог решить, спрашивать ли пользователя перед вызовом20. Значения по умолчанию выбраны по худшему случаю: инструмент без аннотаций считается пишущим, разрушительным, неидемпотентным и выходящим во внешний мир. А главное правило стоит в спецификации предупреждением: «clients MUST consider tool annotations to be untrusted unless they come from trusted servers»11. Сервер, который пишет о себе readOnlyHint: true, может удалять что угодно, и протокол этого не заметит.

Имена тулов спецификация советует держать длиной от 1 до 128 символов из A-Z, a-z, цифр, _, - и точки, уникальными в пределах сервера. Уникальность между серверами — забота клиента: два сервера с тулом search встречаются постоянно, и клиент должен разводить их, например префиксом. Claude Code так и делает: тул query сервера database-tools называется mcp__database-tools__query, а если сервер пришёл в плагине my-plugin, то mcp__plugin_my-plugin_database-tools__query1. Это имя пишут в правила доступа и в матчеры хуков, и хук на короткое имя для плагинного сервера просто не сработает.

Ресурсы и промпты

Ресурс — данные по URI, которые сервер умеет прочитать: файл, строка в базе, страница документации. Сервер отдаёт список (resources/list) и шаблоны вроде travel://activities/{city}/{category}, клиент читает конкретный URI через resources/read. Решает, что положить в контекст, приложение, а не модель: в Claude Code ресурс упоминают в сообщении, например @github:issue://1231. Промпт — именованный шаблон сообщений с аргументами, который пользователь запускает сам; Claude Code показывает промпты серверов в списке команд как /servername:promptname (MCP), а набрать можно и /mcp__servername__promptname.

Оба примитива полезны там, где у тебя есть что-то стабильное для человека: схема базы, которую удобно подложить в разговор, или ритуал «сделай ревью PR по нашему чеклисту». Для всего, что модель должна уметь сделать сама посреди задачи, нужен тул.

Клиентские примитивы и их депрекация

В обратную сторону, от сервера к клиенту, работают ещё три примитива, и вместе с серверными их шесть. Sampling — сервер просит модель клиента что-то сгенерировать и не платит за свой LLM. Roots — клиент сообщает, в каких каталогах серверу разрешено работать. Elicitation, с 2025-06-18, — сервер просит пользователя ввести данные посреди вызова. Рядом с ними жила служебная возможность Logging: сервер шлёт клиенту журнальные сообщения. Примитивом спецификация её не называет, но депрекация зацепила и её.

Ревизия 2026-07-28 объявила устаревшими два клиентских примитива из трёх, Roots и Sampling, а заодно Logging (SEP-2577)3. Из шести примитивов в полную силу остались четыре: инструменты, ресурсы, промпты и elicitation. Работать они продолжат минимум до первой ревизии, вышедшей 28 июля 2027 года или позже17. Замены в списке изменений названы прямо: каталоги передавай параметрами тулов, URI ресурсов или конфигурацией сервера; вместо sampling ходи из сервера в API провайдера модели сам; логи пиши в stderr или в OpenTelemetry. Для трассировки в _meta запроса теперь можно передать traceparent, tracestate и baggage, а уровень логов задаётся полем io.modelcontextprotocol/logLevel в каждом запросе, вместо удалённого logging/setLevel.

Если ты учил MCP по материалам 2025 года, sampling там шёл одной из главных возможностей. Теперь FastMCP 4 убрал ctx.sample() и ctx.list_roots() и советует тем, кому нужна именно модель вызывающего, оставаться на 3.x21. Elicitation уцелел, но устроен теперь иначе.

Сервер спрашивает, не отправляя запросов

Тул, который в FastMCP 3 спрашивал у пользователя дату вылета через await ctx.elicit(...), в FastMCP 4 на соединении новой эпохи падает с ошибкой: «ToolError: elicitation via server-initiated requests is unavailable on 2026-07-28 connections»21. На соединении первой эпохи тот же код работает. Разница в том, что в 2026-07-28 у сервера больше нет права отправлять клиенту запросы.

В первой эпохе elicitation, sampling и roots были встречными запросами: посреди tools/call сервер слал клиенту свой JSON-RPC-запрос elicitation/create и ждал ответа, а по HTTP для этого держал поток SSE, привязанный к сессии. Сессий не стало, и встречный канал пропал вместе с ними. Взамен ревизия 2026-07-28 ввела Multi Round-Trip Requests, MRTR: сервер вместо результата возвращает список того, чего ему не хватает, а клиент собирает ответы и повторяет исходный запрос целиком22. Так выглядит обмен на странице спецификации про инструменты11:

Вернуть input_required могут только tools/call, prompts/get и resources/read. Повтор идёт с новым JSON-RPC id, requestState клиент возвращает байт в байт и не переносит в параллельные запросы. Сервер не вправе просить то, чего клиент не заявил в своих возможностях, и не вправе рассчитывать, что повтор вообще будет: пользователь мог закрыть форму. Ключи в inputRequests выбирает сервер, по ним он потом найдёт ответы. Весь раунд укладывается в обычные запросы и ответы, поэтому повтор может уйти на другую реплику.

Раз сервер ничего не хранит, память о пройденных раундах едет в requestState через клиента. А значит, клиент может её подменить. Спецификация говорит об этом жёстко: сервер «MUST treat requestState as an attacker-controlled input» и, если от этого поля зависит авторизация или бизнес-логика, обязан защитить его целостность, например HMAC или AEAD; в него стоит зашить пользователя, короткий срок жизни и хеш исходного запроса, а одноразовость проверять на сервере22. На странице MRTR в поле для примера так и стоит «AEAD-protected blob», а вот пример со страницы про инструменты выглядит безобидно, пока его не раскодируешь: eyJsb2NhdGlvbiI6Ik5ldyBZb3JrIn0 — это base64 от {"location":"New York"}, открытый JSON, который клиент может переписать как угодно.

В документации FastMCP это называют guard-тулом. request_state=f"dest={destination}" допустим только потому, что подмена города в худшем случае сломает бронирование самому подменившему. Форма или ссылка

В режиме form клиент рисует форму по requestedSchema (плоский объект из строк, чисел, булевых значений и перечислений) и возвращает ответ с action: accept, decline или cancel24. В режиме url, появившемся в 2025-11-25, сервер отдаёт ссылку, и всё происходит вне протокола: пользователь входит на сторонний сайт, платит, подтверждает. Пароли, API-ключи, токены и платёжные данные через форму просить запрещено, для них есть ссылка, и тогда секрет не проходит ни через модель, ни через клиента. Claude Code на соединениях 2026-07-28 заявляет elicitation: {form: {}, url: {}}, показывает диалог сам, а хук Elicitation умеет отвечать без диалога1.

Elicitation в живых серверах Уиллисон не встречал, а в релизном посте MCP приводят опыт Supabase: именно MRTR позволил её серверу без состояния спрашивать пользователя9. Если недостающий параметр модель может спросить у пользователя сама, в чате, elicitation не нужен. Он нужен, когда ответ не должен проходить через модель, как пароль, или когда серверу нужна структурированная форма, которую модель будет заполнять с ошибками.

Долгие операции: Tasks

Сборка, миграция, выгрузка отчёта не укладываются в один HTTP-ответ. В 2025-11-25 для этого появились экспериментальные задачи, в 2026-07-28 их вынесли в расширение io.modelcontextprotocol/tasks и переделали25. Если клиент заявил расширение, сервер может ответить на tools/call не результатом, а resultType: "task" с taskId, pollIntervalMs и ttlMs. Дальше клиент опрашивает tasks/get, а когда задача просит ввод, отвечает через tasks/update. Блокирующего tasks/result и списка tasks/list из экспериментальной версии больше нет. Статус можно не опрашивать, а получать уведомлениями notifications/tasks через subscriptions/listen.

Чего в протоколе на 30 сентября 2026 года нет, так это стандартного способа для сервера самому сообщить агенту о внешнем событии: упал CI, пришло письмо. Claude Code для этого сделал свои каналы (claude/channel), но на соединении новой эпохи канал не зарегистрируется, потому что эта ревизия не может переносить его сообщения1. OpenAI построила MCP Events для ChatGPT на черновом расширении триггеров с доставкой через вебхуки26. Первым пунктом дорожной карты мейнтейнеры поставили как раз это: свести задачи, подписки и прогресс в общие примитивы агентных сообщений18.

Восемьдесят четыре дня. Это крайний случай, но не единственный: у протокола пять ревизий за двадцать месяцев, и в каждой что-то появлялось, а что-то уходило.

Ядро и расширения

Вторая перемена 2026 года — граница между ядром и расширениями. Расширение живёт в своём репозитории, со своей SEP и своими версиями, а включается согласованием: клиент перечисляет поддерживаемые расширения в capabilities.extensions, сервер — в ответе server/discover, и работает пересечение. У официальных расширений имена в пространстве io.modelcontextprotocol/. На сентябрь 2026 года их пять: MCP Apps (io.modelcontextprotocol/ui), Tasks, OAuth Client Credentials для машинного доступа без пользователя, Enterprise-Managed Authorization и Skills37.

MCP Apps даёт инструменту вернуть интерактивный интерфейс: ресурс ui:// с HTML, который хост рисует в изолированном iframe и который общается с хостом сообщениями. Его поддерживают Claude в вебе и на десктопе, VS Code, Microsoft 365 Copilot, ChatGPT, Cursor, Goose и другие. Как отдавать интерфейс из агента и чем MCP Apps отличается от A2UI — в главе 9.

Skills over MCP (SEP-2640, Final 13 сентября 2026 года77) разрешает серверу раздавать скиллы в формате Agent Skills, с SKILL.md и файлами. Сервер отвечает на skills/list и skills/get манифестом, где у каждого файла записаны SHA-256 и размер, а сами байты клиент читает обычным resources/read. Хост обязан сверить хеши, а чтение SKILL.md ещё не активирует скилл: активация остаётся за хостом и идёт через подтверждение36. Поддержка пока тонкая: целиком расширение реализует CLI mcpc, частично ChatGPT, fast-agent и Inspector37. Сами скиллы как формат — в главе 6.

Кто решает и где искать серверы

30 сентября 2026 года полный обход API официального реестра нашёл 37 730 серверов с отметкой «последняя версия» и 126 506 записей о версиях38. В декабре 2025 года Anthropic говорила о «10 000+» опубликованных серверов вообще, не только в реестре30.

Реестр по адресу registry.modelcontextprotocol.io хранит только метаданные28. Запись — это server.json: имя в обратной DNS-нотации вроде io.github.user/server-name, откуда взять пакет или по какому адресу подключиться, как запустить. Код лежит в npm, PyPI и реестрах контейнеров. Кроме владения пространством имён (через GitHub, DNS или HTTP) и защиты от спама, реестр ничего не проверяет, качество и безопасность он оставляет пакетным реестрам и агрегаторам. Приватных серверов там нет. Статус с 8 сентября 2025 года — preview, API v0.1 заморожен 24 октября 2025 года, и README до сих пор предупреждает о возможных несовместимых изменениях и сбросе данных. Так что 37 730 — это число опубликованных карточек, а не работающих серверов.

Свой сервер туда публикуют утилитой mcp-publisher: init собирает черновик server.json, login github подтверждает пространство имён, publish отправляет запись. Для пакета в npm реестр ещё проверяет, что пакет твой: в package.json должно стоять поле mcpName с тем же именем, что в server.json28. Третья строка на графике ниже, MCPB, — это MCP Bundles, бывшие Desktop Extensions: zip с локальным сервером и manifest.json, который Claude для macOS и Windows ставит в один клик39.

Авторизация: от 401 до токена для одного сервера

Клиент впервые обращается к удалённому серверу без токена и получает отказ. Весь поток авторизации MCP разворачивается из одного заголовка этого отказа14:

С ревизии 2025-06-18 MCP-сервер в терминах OAuth — ресурсный сервер, а не сервер авторизации27. Токены выдаёт кто-то другой: корпоративный IdP, Auth0, Keycloak, собственный сервис. Сервер лишь сообщает, к кому идти, через метаданные защищённого ресурса по RFC 9728, и проверяет токены, которые ему приносят. Авторизация при этом необязательна и описана только для HTTP; stdio-сервер берёт секреты из окружения, об этом было выше.

RFC 9728 — метаданные защищённого ресурса: какие серверы авторизации выдают для него токены. RFC 8707 — параметр resource, который привязывает токен к одному ресурсу.

Шаги по порядку. Клиент читает метаданные ресурса и находит в них authorization_servers, затем метаданные сервера авторизации по RFC 8414 или OpenID Connect Discovery; поддерживать клиент обязан оба варианта. Затем регистрируется. Спецификация задаёт порядок: заранее выданные учётные данные, если есть; иначе Client ID Metadata Document; иначе Dynamic Client Registration; иначе спросить пользователя14. Дальше обычный authorization code с PKCE (S256), но с параметром resource, где стоит канонический адрес MCP-сервера, например https://mcp.example.com/mcp, в запросе кода и в обмене на токен. Токен ездит только в заголовке Authorization: Bearer, в строке запроса — никогда.

Почему регистрацию поменяли

В CIMD клиентом выступает URL. Клиент публикует на своём домене JSON и передаёт его адрес как client_id; сервер авторизации скачивает документ во время авторизации, проверяет, что client_id в нём совпадает с адресом, и кеширует по HTTP-заголовкам. Поддержку сервер авторизации объявляет полем "client_id_metadata_document_supported": true.

До этого стандартным путём была динамическая регистрация по RFC 7591: клиент сам вызывает /register и получает свой client_id. Пол Карлтон из основных мейнтейнеров в августе 2025 года объяснил, что с ней не так42: каждое подключение плодит новую регистрацию, одно приложение на разных машинах получает разные идентификаторы, а «An unauthenticated /register endpoint writes to a database within the authorization server». CIMD снимает это сразу, потому что регистрации нет; подробный разбор — в главе 15. В 2025-11-25 его сделали рекомендуемым, в 2026-07-28 DCR перевели в устаревшие, оставив для серверов авторизации, которые CIMD не умеют3.

Ещё две проверки в ревизии 2026-07-28 закрывают атаку подмены сервера авторизации (mix-up). Сервер авторизации возвращает вместе с кодом параметр iss по RFC 9207, и клиент обязан сверить его с тем сервером, к которому посылал пользователя, до обмена кода. А учётные данные клиент хранит с привязкой к издателю и никогда не переносит между серверами авторизации. Claude Code на v2 так и делает: вход с неожиданным издателем завершается ошибкой1. Мелочь, на которой спотыкаются CLI-клиенты с DCR: без application_type: "native" сервер авторизации считает клиента веб-приложением и отвергает redirect на localhost, поэтому ревизия 2026-07-28 обязывает клиента это поле заполнять.

Спецификация авторизации подробная, но реализации разъезжаются: в том же треде жалуются на частые повторные входы из-за offline_access. Для refresh-токенов в 2026-07-28 правило такое: клиент добавляет offline_access, только если сервер авторизации его объявляет, а MCP-сервер не должен требовать его в WWW-Authenticate.

Когда пользователь — сотрудник, а не человек с браузером

Поток выше предполагает человека, который на каждый сервер пройдёт экран согласия. В компании с сотней внутренних серверов это никому не нужно, и на такой случай есть расширение Enterprise-Managed Authorization, стабильное с 18 июня 2026 года35. Клиент меняет ID-токен пользователя от корпоративного IdP на ID-JAG, подписанное IdP разрешение для конкретного MCP-сервера, обменом токенов по RFC 8693. Потом предъявляет ID-JAG серверу авторизации MCP-сервера грантом JWT-bearer. Экрана согласия нет, доступ выдают и отзывают в IdP.

Выданный токен обязан быть ограничен аудиторией MCP-сервера из поля resource в ID-JAG. Оба запроса этого обмена разобраны по полям в главе 15. Для машинного доступа совсем без пользователя есть отдельное расширение OAuth Client Credentials. Но дорожная карта признаёт: идентичность агентов — сабагентов, фоновых задач, делегирования — не решена, и в карте на это стоят DPoP и workload identity federation18. Как устроить OAuth для агентов на своей стороне, от хранения токенов до корпоративного SSO, — в главе 15.

Сервер на Python за вечер

pip install mcp с июля 2026 года ставит версию 2.x, и код из туториалов 2025 года, начинающийся с from mcp.server.fastmcp import FastMCP, перестаёт импортироваться43. Класс в официальном SDK теперь называется MCPServer, типы протокола переехали в отдельный пакет mcp_types (доступны и как mcp.types), а поля моделей в Python стали snake_case: input_schema, is_error, structured_content, хотя на проводе они по-прежнему camelCase. Если мигрировать сейчас некогда, зафиксируй mcp>=1.28,<2: ветка 1.x получает исправления безопасности.

Путаницы добавляет второй FastMCP. Первая версия FastMCP в 2024 году вошла в официальный SDK, а самостоятельный проект живёт у Prefect. FastMCP 4.0.0 вышел 31 августа 2026 года, на 30 сентября актуален 4.0.10, и построен он на SDK v221. У четвёртой версии жёсткие нижние границы зависимостей: pydantic 2.12, Starlette 1.0.1, а значит FastAPI не ниже 0.133.0. Исключения она поднимает из httpx2, поэтому старые except httpx.… молча перестают срабатывать. На соединениях новой эпохи не работают ctx.set_state и Middleware.on_initialize: состояние, которое в FastMCP 3 жило между вызовами, пропадёт, его придётся переносить в хендлы. Задачи включаются только явно: с тулом task=True без mcp.add_extension(TasksExtension()) сервер не стартует21. Prefect пишет в README, что какая-то версия FastMCP работает в 70% MCP-серверов на всех языках44. Проверить это нечем. Из независимого: за 30 дней до конца сентября mcp на PyPI скачали 219 млн раз, fastmcp — 50 млн, причём второй зависит от первого, а в обе цифры входят прогоны CI45.

Для первого сервера бери официальный SDK: зависимостей меньше, и он отвечает обеим эпохам с одного адреса. FastMCP стоит брать, когда нужны его надстройки, а к ограничениям четвёртой версии ты готов. Ниже сервер заказов, по которому сняты все примеры обмена в этой главе. Он запускался на mcp 2.2.0 и Python 3.14 30 сентября 2026 года, данные лежат в SQLite.

Инспектор и его ловушки

MCP Inspector — официальный отладчик, на 23 сентября 2026 года версия 2.8.0, требует Node не ниже 22.19.047. В одном пакете три интерфейса: веб (по умолчанию), --cli для скриптов и CI и --tui для терминала. У каждого подключения есть настройка эпохи, legacy, auto или modern, и разовый запуск CLI по адресу по умолчанию идёт в legacy. Проверил сервер инспектором без флага — проверил старое рукопожатие, а не то, что увидит клиент новой эпохи.

В CI версию инспектора фиксируй точно (@2.8.0, не @2) и задавай --connect-timeout. Две вещи из его README стоит помнить отдельно. На машине без системной связки ключей инспектор по умолчанию сохраняет секреты, включая OAuth-токены, открытым текстом в ~/.mcp-inspector/secrets.json, и в контейнере CI это ровно такая машина. А сам инспектор до версии 0.14.1 позволял выполнить код на машине разработчика без аутентификации через свой прокси, CVE-2025-49596 с оценкой 9,448.

Четыре хоста — четыре разных MCP

Если подключить сервер заказов к Claude Code одной командой из предыдущего раздела, Claude Code будет говорить с ним по-старому, через initialize. Среда выполнения v2, построенная на TypeScript SDK 2.0, предлагает ревизию 2026-07-28 только HTTP-серверам, а stdio-серверам — лишь с переменной MCP_PROTOCOL_NEGOTIATION=auto1. Сама v2 включается по-разному: в сессиях, которые получают флаги функций, — с версии 2.1.232, в остальных (Bedrock, Google Cloud Agent Platform, Microsoft Foundry, выключенная телеметрия) — по умолчанию с 2.1.274. Выбрать среду руками можно через MCP_SDK_GENERATION=v1|v2. Одна и та же команда на двух машинах может дать две разные эпохи.

В Claude Code серверы живут в трёх областях: local (по умолчанию, в ~/.claude.json, только для тебя и только в этом проекте), project (.mcp.json в корне, общий через git) и user (все твои проекты). Серверы из .mcp.json требуют подтверждения, а с версии 2.1.196 одобрения из файлов в репозитории учитываются только после того, как ты доверился рабочей папке. Ответ тула больше 25 тыс. токенов (MAX_MCP_OUTPUT_TOKENS) уходит на диск, а в разговоре остаётся ссылка на файл; подробнее об усечении в главе 3. Вызов без ответа и прогресса Claude Code обрывает через 5 минут для удалённых серверов и через 30 для stdio.

Cursor поддерживает stdio, SSE и Streamable HTTP, из примитивов — инструменты, промпты, ресурсы, roots, elicitation и MCP Apps; о sampling и ревизии 2026-07-28 в его документации ни слова49. Конфигурация в .cursor/mcp.json проекта или в ~/.cursor/mcp.json, с подстановками вроде ${env:NAME}, а в корпоративном тарифе есть белый список серверов. VS Code хранит серверы в mcp.json, умеет подхватывать серверы, уже настроенные в Claude Desktop, даёт включать и выключать отдельные тулы и на macOS и Linux запускает stdio-серверы в песочнице с ограничением файловой системы и сети50.

У OpenAI интеграции в ChatGPT и Codex теперь называются плагинами, и документация для них описывает обычные MCP-серверы с произвольными тулами, structuredContent, outputSchema и аннотациями5. Жёсткая форма из двух тулов, search и fetch, нужна только для deep research и корпоративного поиска; старые статьи, которые выдают её за всю поддержку MCP в ChatGPT, устарели. Вход — через метаданные ресурса и resource, CIMD в приоритете, если сервер авторизации его объявляет. Сколько стоят описания инструментов

В ноябре 2025 года Anthropic посчитала обычную рабочую связку из пяти серверов: GitHub, Slack, Sentry, Grafana и Splunk, 58 инструментов. Их описания заняли около 55 тыс. токенов до первого сообщения пользователя, а худший случай во внутренних замерах компании доходил до 134 тыс. токенов53. Армин Ронахер в декабре жаловался, что один сервер Sentry «out of the box» съедает около 8 тыс. токенов54. Из 55 тыс. на GitHub приходится 26 тыс. за 35 тулов, а на Slack 21 тыс. за одиннадцать: цену сервера задаёт длина описаний, а не число тулов. Как писать описания короче и сколько стоят другие популярные серверы, разобрано в главе 3; здесь важнее, что с этим могут сделать протокол и хост.

Токены — половина беды, вторая половина — точность выбора. Документация Anthropic по поиску тулов говорит, что выбор нужного инструмента «degrades once you exceed 30–50 available tools»55. Это утверждение вендора без опубликованных данных, но независимые замеры показывают то же направление. В работе RAG-MCP (май 2025) на стресс-тесте с растущим числом MCP-тулов точность выбора выросла с 13,62% до 43,13%, когда описания отбирал поиск, а промпт сократился больше чем вдвое56. GitHub в ноябре 2025 года сократил встроенные тулы Copilot с 40 до 13 и получил плюс 2–5 процентных пунктов на SWE-bench Verified и SWE-Lancer и минус 400 мс задержки57.

И даже когда модель видит только нужное, работа с настоящими MCP-серверами остаётся трудной. В бенчмарке MCPMark (127 задач на создание, чтение, изменение и удаление данных) лучшая модель сентября 2025 года, gpt-5 с medium reasoning, решила 52,56% задач с первой попытки и 33,86% — во всех четырёх попытках подряд; claude-sonnet-4 и o3 не дотянули до 30%, а на задачу в среднем уходило 16,2 хода и 17,4 вызова тулов58. Цифрам год, но порядок полезно помнить, когда обещаешь, что агент «просто сходит в CRM».

Три способа не платить за всё сразу

Первый — поиск по тулам (tool search). Хост отдаёт модели имена тулов и инструкции серверов, а полные схемы подгружает, когда модель их нашла. На уровне API у Anthropic это серверные тулы tool_search_tool_regex_20251119 и tool_search_tool_bm25_20251119 плюс флаг defer_loading у отложенных тулов; по данным компании, это экономит 85% токенов на описаниях53.

В Claude Code поиск включён по умолчанию, но выключается незаметно. Так бывает, когда ANTHROPIC_BASE_URL указывает не на Anthropic: большинство корпоративных прокси не пропускают нужные для поиска блоки, и вернуть его можно только явным ENABLE_TOOL_SEARCH. Ещё поиск выключает CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS, и тогда его не вернуть. Claude Code советует авторам серверов вкладываться в instructions: при поиске это единственное, что модель видит о сервере до того, как решит искать его тулы1. Включать поиск в твоём клиенте Anthropic советует с 10 тыс. токенов описаний или с десятка тулов53, а рекомендации для клиентов MCP — с 1–5% окна контекста59. Механика поиска у разных вендоров разобрана в главе 3, а то, как он ведёт себя с кешем промпта, — в главе 2.

Второй — исполнение кода поверх MCP. Anthropic описала его 4 ноября 2025 года: серверы показываются модели как файловая система с TypeScript-функциями, модель пишет скрипт, скрипт выполняется в песочнице и зовёт тулы, а в контекст возвращается только то, что скрипт напечатал60. В посте есть пример: стенограмму двухчасовой встречи из Google Drive надо положить в запись Salesforce. Обычными вызовами текст проходит через модель дважды, на чтении и на записи, это около 50 тыс. лишних токенов. В скрипте он в контекст не попадает вообще:

Там же фигурирует цифра, которую часто цитируют неправильно: 150 тыс. токенов против 2 тыс., минус 98,7%. Это вообще не замер, а иллюстрация к другому приёму: агент просматривает «файловую систему» серверов и грузит только нужные описания. Настоящий замер у Cloudflare: весь её API, больше 2500 эндпоинтов, в виде обычных тулов занял бы 1,17 млн токенов, а в виде двух тулов, search и execute, помещается примерно в тысячу61. Цена приёма — песочница, в которой исполняется написанный моделью код. Anthropic оговаривает, что для него нужны «appropriate sandboxing, resource limits, and monitoring», и в разделе о безопасности видно, что песочницы тоже ломают.

Третий способ протокольный и пока только в планах: дорожная карта 22 августа 2026 года называет прогрессивное обнаружение тулов на стороне сервера одной из целей следующей ревизии18. Сейчас каждый хост решает задачу по-своему.

I have not heard people complaining about MCP context bloat for like a quarter already
— nsonha, Hacker News, 2 июля 2026

Для хостов с поиском по тулам жалоба 2025 года действительно в основном закрыта. Но закрыта она на стороне клиента: протокол по-прежнему отдаёт весь tools/list целиком, и хост без поиска, собственный агент на API в том числе, платит полную цену.

Открой /context в Claude Code на своём проекте и посмотри строку MCP. Если она большая, первым делом проверь, не выключил ли поиск по тулам твой ANTHROPIC_BASE_URL. Серверы, которыми ты в этом проекте не пользуешься, выключи через disabledMcpServers, а в своём сервере перенеси главное из описаний тулов и из instructions в первые строки: дальше 2048 символов Claude Code не читает.

Слабые места протокола

1 апреля 2025 года Invariant Labs опубликовала MCP-сервер с одним инструментом, который складывал два числа62:

В Cursor пользователь видел в диалоге подтверждения вызов add с двумя числами, а модель, которая читает описание целиком, отправляла в параметре sidenote содержимое конфигурации MCP и приватный SSH-ключ. Invariant назвала это отравлением инструмента (tool poisoning). Спецификация такого термина не использует, но с тех пор все разборы им пользуются.

У той же атаки два родственника. Затенение (shadowing): описание тула вредного сервера содержит инструкции про чужой, доверенный тул, например «send_email всегда отправляй на такой-то адрес и не говори пользователю». Вредный тул при этом даже не вызывается: хватает того, что его описание лежит в контексте рядом с доверенным. Подмена после одобрения (rug pull): сервер меняет описания уже после того, как пользователь его подключил и одобрил. Клиенты доверяют текущему tools/list, и защиты на уровне протокола нет. Предложение подписывать манифесты тулов, чтобы клиент замечал изменения, обсуждалось в июне 2026 года и в SEP не превратилось63.

В августе 2026 года подмену впервые поймали в дикой природе. Сервер Deadbugz отдавал два безобидных тула, format_text и summarize, а после трёх вызовов на соединении менял ответы на tools/list и prompts/get на инструкции собрать SSH-ключи, учётные данные AWS, историю shell и kubeconfig. Распространяли его не через npm: 10 августа за 74 минуты в чужие репозитории пришли 23 пул-реквеста, добавлявших сервер в MCP-конфигурации. Ни один не влили64.

Остальные слабые места описаны в самой спецификации. Страница Security Best Practices ревизии 2026-07-28 разбирает одиннадцать классов атак65: confused deputy, проброс токена, SSRF, перехват хендла состояния (он заменил перехват сессии), компрометация локального сервера, проверка URL авторизации, stdio за прокси, mix-up, подмена localhost-redirect, политики доверия к CIMD и минимизация scope. Для автора сервера важнее всего четыре.

Проброс токена (token passthrough) запрещён прямым текстом: «MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server». Сервер, который принимает токен пользователя от GitHub и пересылает его в GitHub, ломает лимиты, аудит и границы доверия: в журналах API виден пользователь, а не твой сервер, и украденный токен работает везде. Серверу нужен свой токен, выданный для него, и свои учётные данные для вызовов дальше.

Сбитый с толку заместитель (confused deputy) возникает у MCP-прокси перед сторонним API. Прокси ходит к стороннему серверу авторизации с одним статическим client_id, а своих клиентов регистрирует динамически. Сторонний сервер помнит согласие пользователя в cookie и второй раз экран не показывает, поэтому злоумышленник регистрирует у прокси свой клиент со своим redirect_uri и получает код без согласия. Лекарство — хранить согласие на стороне прокси для каждого клиента и проверять его до перенаправления, а cookie делать __Host-, Secure, HttpOnly, SameSite=Lax и привязывать к client_id.

SSRF встречается в разобранных CVE по MCP чаще других классов. Вредный сервер может указать в resource_metadata или authorization_servers адрес 169.254.169.254, и клиент сам туда сходит; то же грозит серверу авторизации, скачивающему документ CIMD. 28 июля 2026 года HashiCorp раскрыла сразу несколько уязвимостей в своём Terraform MCP-сервере: SSRF, через который утекал собственный bearer-токен сервера, обход авторизации через кеш учётных данных сессии в режиме с состоянием (CVE-2026-16496) и повторное использование учётных данных между арендаторами в режиме без состояния (CVE-2026-16498)66. Утекало в обоих режимах, так что отказ от сессий сам по себе ничего не защищает. Через три дня NVD опубликовала SSRF в официальном MCP Toolbox от Google, CVE-2026-14540: HTTP-клиент инструментов шёл за любым редиректом и не проверял адрес назначения, и параметр от промпт-инъекции уводил запрос во внутреннюю сеть67. А ещё в июле 2025 года выход за пределы разрешённых каталогов через симлинки нашли в эталонном Filesystem-сервере из репозитория самого MCP, CVE-2025-5310968. Официальный статус сервера не заменяет проверку путей и адресов.

Локальный сервер запускается с правами пользователя, поэтому команда запуска в «установке в один клик» — это исполнение кода. Спецификация требует показывать команду целиком, без сокращений, перед такой установкой. Отдельный случай — клиент, который открывает присланный сервером адрес авторизации: в прокси mcp-remote подделанный authorization_endpoint приводил к выполнению команд ОС, CVE-2025-6514 с оценкой 9,669.

Исполнение кода, лучшее средство от раздувания контекста, переносит риск в песочницу. В августе 2026 года Check Point показала на Black Hat пять ошибок в workerd, на котором работает Code Mode у Cloudflare, включая чтение секретов соседних арендаторов и use-after-free в zlib с выходом в нативный код хоста, «starting from a prompt injection»70. В облаке Cloudflare ошибки исправлены, самостоятельным установкам нужен workerd v1.20260619.1 или новее.

Насколько всё это массово, пытался измерить Canopii, продавец MCP-шлюза, так что к цифрам стоит относиться как к отчёту вендора. В июне 2026 года компания просканировала 11 524 сервера: 830, каждый четырнадцатый, получили оценку D или F; 184 случая подмены описаний между версиями у 170 серверов; из серверов, заявивших авторизацию, 31% её не проверял; у 232 серверов нашлись опасные места вроде eval (141), внедрения команд (69) и небезопасной десериализации (42); 78% не закрепляют версии зависимостей; ни одного подписанного релиза; а серверы с тысячей звёзд на GitHub оказались высокорисковыми в 5,3 раза чаще, чем малоизвестные71.

Почти всё, что здесь делается руками, в компании сводят в шлюз между хостами и серверами. На нём можно собрать много серверов за одним эндпоинтом, пропускать только разрешённые серверы и тулы (и заодно укоротить tools/list), закрепить версии и заново требовать одобрения, когда описание изменилось, писать аудит по каждому вызову и менять токен пользователя на токен для конкретного сервера вместо проброса. Готовые продукты есть, их возможности известны со слов вендоров. Microsoft Foundry называет свой вариант «toolbox unified MCP endpoint»9. Prefect Horizon обещает RBAC на уровне тулов и журналы аудита44, Stacklok ToolHive, открытый под Apache-2.0 7 сентября 2026 года, запускает каждый сервер в своём контейнере, собирает их за «Virtual MCP Server» и подписывает записи своего реестра72. Протокольная опора для таких шлюзов — заголовки Mcp-*, с оговоркой про старые версии из раздела о заголовках. И всё это работает при одном условии: до сервера нельзя достучаться в обход шлюза. Как шлюз меняет токены, разобрано в главе 15.

Фиксируй версии серверов (npx -y pkg@1.4.2, а не голое имя пакета), смотри изменения .mcp.json в пул-реквестах так же внимательно, как код, и не держи в одной сессии сервер с приватными данными и сервер, который читает чужой контент: вместе с любым каналом наружу это готовая утечка. Изменённое описание тула считай новым сервером, которому нужно новое одобрение. Атаки и защиты подробно — в главе 16.

MCP или CLI со скиллами

20 сентября 2026 года пост «MCP was always a bad idea?» собрал на Hacker News 335 очков. Мысль знакомая: у агента в терминале есть shell, CLI-утилиты он знает из обучения, скиллы объясняют ему, как ими пользоваться, и протокол со схемами и серверами становится лишним слоем. Саймон Уиллисон ответил в треде так:

Sure, there's almost no reason to use MCPs if you are running a full-blown terminal agent (Claude Code, Codex, Meta Muse, OpenClaw etc) with unfettered internet access - just let it call APIs directly. If you want to operate something that's less YOLO than that, you'll find yourself wanting: 1. Control over exactly which external services it can access 2. A way to handle authentication that doesn't allow the agent to directly access API keys 3. A sensible UI to allow users to connect and authenticate further services 4. Strong audit logging for what's going on
— Саймон Уиллисон, Hacker News, 20 сентября 2026

Для агента в терминале без ограничений MCP почти не нужен. Нужен он там, где требуются контроль над внешними сервисами, авторизация без доступа агента к ключам, интерфейс подключения и аудит. На следующий день Уиллисон добавил: агент, который может запустить CLI, почти наверняка может достать и ключи этой CLI, вплоть до того, чтобы переписать бинарник.

Самый цитируемый технический аргумент против MCP для кодовых агентов написал Армин Ронахер в декабре 2025 года54. У серверов нет стабильного API: «MCP servers have no desire to maintain API stability», и Sentry у него на глазах поменял синтаксис поиска, обесценив его собственные заметки. Описание тула — плохой компромисс: «The description is both too long to eagerly load it, and too short to really tell the agent how to use it». А скиллы выигрывают потому, что модель уже хорошо умеет звать команды через bash: «The reinforcement learning that made the Claude family of models very good tool callers just helps with these newly discovered tools».

Ещё в августе 2025 года Марио Цехнер сравнил одно и то же в цифрах: тул управления терминалом в виде MCP-сервера и в виде CLI, три задачи, по десять прогонов в Claude Code73. Обе версии решили всё. MCP-версия оказалась немного дешевле и быстрее, $19,45 и 51 минута против $19,95 и 66 минут. Вывод при этом он сделал обратный тому, что обычно из этих цифр извлекают: сначала сделай хорошую CLI, она «simpler and more portable», обёртку MCP добавь, если понадобится, потому что «the protocol is just plumbing». Решает качество инструмента, а не транспорт.

MCP makes a lot, lot more sense when you think of it as an auth standard and not a comparison with CLIs
— martinald, Hacker News, тред Launch HN: Manufact, 2 июля 2026

Главное в MCP, по этой версии, — стандартная авторизация, которой у CLI нет. В треде «Ask HN: Who is using MCP in production?» 3 сентября 2026 года ответы разошлись так же: одни зовут gh вместо GitHub-сервера, потому что так «waaay cheaper», другие пишут внутренние серверы, которые прячут от агента несколько унаследованных систем за одним интерфейсом. Это отдельные рассказы, а не опрос.

29 сентября, через девять дней после поста о «плохой идее», команда Earendil, которая раньше публично отказывалась от MCP, объявила, что встроила его в своего агента Pi74. Объяснение короткое: «The world is not static». Встроили через Codemode, JavaScript-песочницу в харнессе, которая зовёт тулы, не сваливая их результаты в контекст. А будущее MCP в Earendil видят «much closer to OpenAPI with intelligent tool discovery».

Уиллисон тем же путём прошёл ещё 31 июля, через три дня после выхода ревизии 2026-07-28. По его словам, MCP «became somewhat eclipsed by Skills», но инструменты MCP проще проверять и ограничивать, а протокол без состояния сильно упростил и клиенты, и серверы, поэтому «I'm coming back around to MCP now»75. GitHub 18 сентября ответил на тот же вопрос в блоге так: MCP стандартизирует интерфейсы, скиллы упаковывают знание о процессе, и одно другого не отменяет76. Расширение Skills over MCP их и соединяет: сервер раздаёт скиллы вместе с тулами.

Спор на самом деле о том, где проходит граница доверия. Если агент работает в твоём репозитории, у него есть shell и есть хорошая CLI (gh, kubectl, psql), бери CLI и скилл, который объясняет, как ею пользоваться в вашем проекте: дешевле по контексту, модель знает инструмент, отлаживать проще. Если сервис удалённый, нужен вход под конкретным пользователем, аудит или хост без shell (ChatGPT, Claude в браузере, агент на Messages API), бери MCP. Оценка меняется, как только агент читает чужой контент: письма, тикеты, веб-страницы. Тогда промпт-инъекция становится реальной, и довод Уиллисона про ключи вне досягаемости агента перевешивает экономию токенов, даже для кодового агента.

Проверь себя

Клиент отправил HTTP-серверу tools/call ревизии 2026-07-28 и получил 400. Что он должен сделать дальше?

Смотря что в теле. -32022 со списком supported — сервер новый, повтори запрос с версией из списка; -32020 или -32021 — сервер новый, чини сам запрос. Пустое или чужое тело — Streamable HTTP первой эпохи, начинай с initialize. Так же читают и 404: с -32601 это новый сервер без такого метода, без JSON-RPC-тела — возможно, HTTP+SSE, и клиент пробует GET и ждёт событие endpoint.

После перехода на 2026-07-28 липкую маршрутизацию на балансировщике можно выключить. Почему о состоянии всё равно придётся думать?

Исчезла протокольная сессия, а состояние приложения осталось: корзина, транзакция, пройденные раунды диалога. Оно переехало в хендлы в аргументах тулов и в requestState, которые носит клиент или модель. Хендл надо привязать к пользователю и дать ему срок жизни, requestState подписать.

Чужой сервер помечает все свои тулы readOnlyHint: true. Можно ли на этом основании вызывать их без подтверждения?

Нет. Аннотация — заявление сервера о себе, протокол её не проверяет, и спецификация велит считать аннотации недоверенными, если сервер не доверенный. Для своего сервера, где подсказка подкреплена кодом (база открыта в mode=ro), можно.

Клиент по HTTP отвалился посреди tools/call, который списывает деньги. Что это значит для сервера новой эпохи и как к этому готовиться?

Закрытый поток ответа сервер обязан считать отменой запроса, отдельного notifications/cancelled по HTTP не будет, а сам клиент, скорее всего, повторит запрос с новым id. Значит, тул может оборваться на середине и прийти ещё раз. Списание делают в транзакции и с ключом идемпотентности, чтобы повтор не списал дважды, а долгую работу выносят в задачи.

Что произойдёт, если в stdio-сервере оставить в теле тула print("debug:", rows)?

Строка уйдёт в stdout, где клиент ждёт только сообщения JSON-RPC, по одному на строку. Спецификация это запрещает, а что клиент сделает с мусором, не определено: может пропустить строку, может закрыть соединение. Отладочный вывод идёт в stderr.

Тул в режиме MRTR кладёт в requestState base64 от {"order_id": 1001, "approved": true}. Что здесь не так?

requestState проходит через клиента, и спецификация требует считать его вводом атакующего. Клиент перепишет approved и получит одобренный заказ. Раз от поля зависит бизнес-логика, его надо защитить HMAC или AEAD, зашить внутрь пользователя, короткий срок и хеш исходного запроса, а одноразовость проверять на сервере.

Зачем серверу сверять заголовок Mcp-Name с именем тула в теле, если JSON всё равно разбирает он сам?

Потому что решения до него принимает шлюз, который тело не читает: маршрут, лимиты, запреты. Если сервер выполнит то, что в теле, запрос с разрешённым find_orders в заголовке и delete_orders в теле обойдёт политику шлюза. Поэтому при расхождении ответ 400 с кодом -32020.

Что ломается, если MCP-сервер принимает токен пользователя от GitHub и пересылает его в API GitHub?

Это проброс токена, спецификация его запрещает. Сервер принимает токен, выданный не ему, так что проверка аудитории теряет смысл и украденный токен работает везде, а в журналах GitHub виден пользователь, а не твой сервер. Серверу нужен свой токен и свои учётные данные для вызовов дальше.

Хост без поиска по тулам подключил пять серверов из примера Anthropic. Какие две цены он платит на каждом шаге?

Около 55 тыс. токенов описаний в каждом запросе и худший выбор инструмента: чем длиннее список, тем чаще модель берёт не тот тул. Снижают обе цены поиск по тулам с отложенной загрузкой, исполнение кода поверх MCP и выключение серверов, которые в проекте не нужны.

Почему проверка сервера при подключении не поймала бы Deadbugz?

Первые три вызова сервер отдавал чистые описания и только потом подменял tools/list и prompts/get. Одобрение привязано к имени сервера, а подписи манифестов в протоколе нет. Помогают закреплённые версии, новое одобрение при изменении описаний и ревью .mcp.json в пул-реквестах.

Inspector CLI без флагов прошёл по твоему HTTP-серверу без ошибок. Почему этого мало?

Разовый запуск CLI по умолчанию идёт в эпохе legacy, то есть проверено старое рукопожатие. Claude Code и другие клиенты новой эпохи пойдут к HTTP-серверу по ревизии 2026-07-28, и этот путь остался непроверенным. Нужен прогон с --protocol-era modern.

Кодовому агенту в репозитории нужен доступ к трекеру задач. Когда ты выберешь CLI со скиллом, а когда MCP-сервер?

CLI со скиллом, если у агента есть shell, у трекера есть хорошая CLI и агент не читает недоверенный контент. MCP, если нужен вход под конкретным пользователем, аудит, работа из хоста без shell, или агент читает тикеты, которые пишут посторонние: тогда промпт-инъекция реальна, и ключи должны лежать вне досягаемости агента.
