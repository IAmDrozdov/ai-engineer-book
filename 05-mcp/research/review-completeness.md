## 1. [critical] Рисунок fig-era-probe и ответ в «Проверь себя» отправляют клиента в initialize на любой 404

**Где:** «Как клиент угадывает эпоху сервера» (строка 273, переход `try --> init: 400 без JSON-RPC или 404`). Ещё «Проверь себя», первый вопрос (строка 964): «Тот же откат нужен при 404 без JSON-RPC».

**Что не так.** Раздел Backward Compatibility спецификации 2026-07-28 (Streamable HTTP) даёт три разных исхода:
- Сервер новой эпохи на неизвестный метод отвечает `404 Not Found` с JSON-RPC-ошибкой `-32601`. Цитата: «The JSON-RPC error body distinguishes this case from a `404` returned by a legacy HTTP+SSE server». По рисунку, где стрелка в initialize подписана просто «404», клиент откатится в первую эпоху на совершенно новом сервере.
- `400` с пустым или нераспознанным телом означает откат в `initialize`, то есть Streamable HTTP первой эпохи.
- `400`, `404` или `405` без распознанной ошибки новой эпохи означают пробу старого HTTP+SSE: GET, затем ждать событие `endpoint`. Это не `initialize` по POST. На рисунке этой ветки нет, а в ответе из «Проверь себя» при «404 без JSON-RPC» стоит не тот шаг.
- Среди распознанных ошибок `400` спецификация называет ещё `MissingRequiredClientCapabilityError` (-32021), а на рисунке есть только -32022.

**Что сделать.** Перерисовать диаграмму состояний так:
- `200` → новая эпоха;
- `400` + -32022 → повтор с версией из `supported`;
- `400` + -32021 или -32020 → исправить запрос;
- `404` + -32601 → сервер новый, метода нет;
- `400` с пустым или чужим телом → `initialize`;
- `400`/`404`/`405` без JSON-RPC → GET и ожидание `endpoint` (HTTP+SSE).

Ответ в «Проверь себя» поправить так же.

**Источник:** Streamable HTTP, спецификация 2026-07-28, разделы «Request Metadata» и «Backward Compatibility», https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http (проверено 30.09.2026). В заметках: `gaps.md`, «HTTP status semantics», строка 156 («Unknown method → 404 + -32601»).

## 2. [major] Политику шлюза по заголовкам можно обойти старой версией протокола

**Где:** «Заголовки для тех, кто не читает тело» (строки 217–236).

**Что не хватает.** Глава говорит, что сверка заголовков с телом закрывает обход политики шлюза («Иначе шлюз пропустит запрос по безобидному Mcp-Name…»). Это верно только для запросов 2026-07-28. Двухэпохальный сервер вроде того, что в самой главе (mcp 2.2.0), на запрос с `MCP-Protocol-Version: 2025-11-25` заголовки `Mcp-*` не сверяет. Спецификация прямо требует этого от посредников: «Intermediaries that enforce policy based on mirrored headers … SHOULD verify that the MCP-Protocol-Version header indicates a version that requires header–body validation. If the version is older or the header is absent, the intermediary SHOULD reject the request».

**Что сделать.** Добавить абзац из двух-трёх предложений после примера с -32020: шлюз, который решает по `Mcp-Name`, должен отбрасывать версии старше 2026-07-28 или разбирать тело сам. Хорошо ляжет и в подпись к fig-modern-routing. Ещё одна деталь оттуда же: не-ASCII имена и значения идут в заголовке в виде `=?base64?…?=`, и сервер сравнивает их с телом после декодирования.

**Источник:** та же страница Streamable HTTP, «Server Validation» (примечание для intermediaries) и «Value Encoding». В заметках: `gaps.md`, строка 160.

## 3. [major] Отмена и прогресс в новой эпохе: разрыв соединения означает отмену

**Где:** «Streamable HTTP в новой эпохе» (строки 288–306). Туда же ведут связи с «Долгие операции: Tasks» и с таймаутами Claude Code в разделе о клиентах.

**Что не хватает.** Прогресс упомянут («в нём едут уведомления о прогрессе»), отмены в главе нет вовсе. Этого нет и в заметках. По спецификации 2026-07-28:
- По Streamable HTTP закрытие SSE-потока ответа и есть отмена: «Closing the SSE response stream MUST be treated by the server as cancellation of that request». `notifications/cancelled` по HTTP не шлют.
- По stdio клиент обязан отправить `notifications/cancelled` с `requestId`.
- Сервер сам шлёт `notifications/cancelled` только для закрытия потока `subscriptions/listen`.
- Прогресс: клиент кладёт `progressToken` в `_meta` запроса, сервер шлёт `notifications/progress` с монотонно растущим `progress`, необязательными `total` и `message`, только в поток этого запроса, не в listen-поток.
- Таймауты: по прогрессу их можно продлевать, но максимальный таймаут соблюдать всегда.

Бэкендеру отсюда нужно следствие. Обрыв соединения балансировщиком, таймаут клиента (у Claude Code 5 минут для удалённых серверов) или закрытая вкладка останавливают работу тула на середине. Вместе с уже написанным в главе «повтор после обрыва спишет деньги дважды» это даёт правило: запись делать транзакционно или идемпотентно по ключу, а долгую работу выносить в Tasks. Ещё две ловушки с той же страницы: сервер должен ставить `X-Accel-Buffering: no`, иначе nginx копит SSE, а долгий поток `subscriptions/listen` держат живым строками-комментариями `:`.

**Что сделать.** Абзац и короткий пример JSON с `progressToken` и `notifications/progress` в разделе про Streamable HTTP. Строку «отмена» добавить в таблицу «До 2025-11-25 / С 2026-07-28»: раньше было уведомление, теперь закрытие потока. Пункт в «Проверь себя»: «клиент отвалился посреди `tools/call`, списывающего деньги, — что сервер обязан сделать?».

**Источник:** Cancellation, https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation; Progress, https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/progress; Streamable HTTP, раздел «Cancellation» и «Receiving Messages». Все проверены 30.09.2026.

## 4. [major] Шлюзы как средство защиты не раскрыты, хотя охват их прямо называет

**Где:** «Три способа не платить за всё сразу» (строка 856) или конец раздела «Слабые места протокола» (перед абзацем «Фиксируй версии серверов…»).

**Что не хватает.** В охвате среди защит названы три: tool search, code execution и gateways. В главе шлюз встречается только как потребитель заголовков `Mcp-*` и в оговорке «Canopii, продавец MCP-шлюза». При этом на шлюзе сходится почти всё, что глава советует делать руками:
- собрать много серверов за одним эндпоинтом;
- белый список серверов и тулов, чтобы отфильтрованный `tools/list` занимал меньше токенов;
- закрепить версии и заново одобрять изменившиеся описания (защита от rug pull);
- аудит на уровне отдельного тула;
- обмен токенов вместо их проброса.

Заметки приводят примеры: Stacklok ToolHive (открыт под Apache-2.0 7 сентября 2026: отдельный контейнер на сервер, «Virtual MCP Server», подписанный реестр), Prefect Horizon («tool-level RBAC, audit logs»), единый MCP-эндпоинт toolbox в Microsoft Foundry. Глава 15 разбирает Kong `ai-mcp-oauth2` и agentgateway. Условие, при котором шлюз работает: до сервера нельзя достучаться в обход шлюза. Оно уже сформулировано в главе 15.

**Что сделать.** Сделать способов четыре или добавить в раздел о безопасности абзац «Шлюз между хостом и серверами»: что он делает, три примера с пометкой «описано вендором», протокольная зацепка (`Mcp-*` из раздела о заголовках плюс находка 2 про версии) и ссылка на главу 15 «Шлюз, который меняет токены». Рисунок не нужен: fig-modern-routing уже показывает шлюз.

**Источник:** `gaps.md`, «Gateways and hardening products» (строки 366–369; [G2], [G17], [G45]); глава 15, раздел «Шлюз, который меняет токены».

## 5. [major] Нет автотестов сервера, только ручная проверка Inspector

**Где:** «Сервер на Python за вечер» / «Инспектор и его ловушки» (строки 722–795) и «Чеклист навыков».

**Что не хватает.** Для бэкендера сервер без pytest не закончен. В главе ручной Inspector и Inspector CLI в CI, но нет теста в процессе, хотя официальный SDK v2 умеет это одной строкой: `Client` принимает объект сервера и работает в памяти, без подпроцесса и сети. Пример из документации SDK:

```python
@pytest.fixture
async def client():
    async with Client(mcp, raise_exceptions=True) as c:
        yield c

@pytest.mark.anyio
async def test_call_add_tool(client: Client):
    result = await client.call_tool("add", {"a": 1, "b": 2})
```

Инструмент такого теста — `structured_content` (snake_case, как и сказано в главе), а не текст. Разделение ролей понятное: тест в памяти проверяет логику тулов и схемы, а Inspector CLI с `--protocol-era modern` проверяет провод и HTTP.

**Что сделать.** Пятый шаг в списке «Поставь зависимости → … → Посмотри состояние»: тест `find_orders` на `Client(mcp)`, 10–12 строк на демо-сервере. Нужно прогнать, как остальные примеры главы. В «Чеклист навыков» добавить пункт «Покрываю тулы тестами на in-memory `Client`».

**Источник:** документация MCP Python SDK, «Testing», https://py.sdk.modelcontextprotocol.io/get-started/testing/ (проверено 30.09.2026); `spec.md`, строки 418–422 (класс `Client` в v2).

## 6. [major] Когда поиск по тулам в Claude Code выключен

**Где:** «Три способа не платить за всё сразу» (строка 857: «В Claude Code поиск включён по умолчанию для моделей начиная с поколения 4.5») и совет «Открой /context…».

**Что не хватает.** По документации Claude Code, которую `gaps.md` разбирает в противоречии №2, поиск выключается в трёх случаях:
- `ANTHROPIC_BASE_URL` указывает не на первичный эндпоинт Anthropic (корпоративный LLM-прокси, LiteLLM и т. п.);
- задана переменная `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`;
- модель старше поколения 4.5.

Выключить его вручную можно через `ENABLE_TOOL_SEARCH=false`. Для читателя в компании, где запросы идут через шлюз, это главное. Цитата nsonha и вывод главы «жалоба 2025 года в основном закрыта» у него не работают: все описания снова в каждом запросе, и об этом ничего не предупреждает. Поле «MCP» в `/context` это покажет, и вывод главы стоит завязать именно на этот признак.

**Что сделать.** Одно-два предложения после «включён по умолчанию…»: условия выключения и переменная. В абзаце с `/context` добавить: «если строка MCP большая, проверь, не выключен ли поиск из-за `ANTHROPIC_BASE_URL`».

**Источник:** `gaps.md`, «Contradictions resolved» №2 ([G21] https://code.claude.com/docs/en/mcp); `practice.md`, строка 225 (`ENABLE_TOOL_SEARCH=false`).

## 8. [major] В главе нет справочной таблицы кодов ошибок и HTTP-статусов новой эпохи

**Где:** «Что сервер говорит о себе» или «Заголовки для тех, кто не читает тело».

**Что не хватает.** Коды разбросаны по тексту: -32601, -32602, -32020, -32022, диапазон -32020…-32099. Нет двух изменений, на которых ломается миграция:
- «ресурс не найден» теперь `-32602` (Invalid Params), а не `-32002`: SEP-2164, ревизия 2026-07-28. Клиент, который ловит -32002, молча перестанет отличать отсутствующий ресурс;
- новый `-32021` MissingRequiredClientCapability, тоже с HTTP 400.

Нет и HTTP-стороны ответа, которую сервер обязан держать: `202 Accepted` без тела на уведомление, `403` на чужой `Origin`, `404` с -32601 на неизвестный метод, `405` на GET/DELETE, `400` для -32020/-32021/-32022. Диапазон -32000…-32019 остаётся за реализациями. Тому, кто откроет главу как справочник, нужна одна таблица, а не поиск по шести разделам.

**Что сделать.** Таблица «Ситуация → HTTP-статус → JSON-RPC-код» на 8–9 строк. Она же закроет находку 1: 404 с -32601 против 404 без тела.

**Источник:** `gaps.md`, «Claims most likely to be wrong» №9 (строка 38) и «HTTP status semantics» (строки 155–160); Streamable HTTP 2026-07-28, «Sending Messages» (202) и «Security & Endpoint» (403).

## 9. [minor] Реестр: как опубликовать свой сервер и что такое MCPB

**Где:** «Кто решает и где искать серверы» (строки 612–627) и график fig-registry-packages (строка 618).

**Что не хватает.** Реестр описан как каталог, но автор сервера, для которого написана глава, не узнаёт, как туда попасть. Путь такой:
- `mcp-publisher init` создаёт `server.json`;
- `mcp-publisher login github` — вход;
- `mcp-publisher publish` — публикация.

Пакет связывают с записью полем `"mcpName": "io.github.<user>/<server>"` в `package.json`: так реестр проверяет, что пакет принадлежит владельцу пространства имён.

На графике третья по величине строка — «MCPB, 1374», а в тексте этот термин не объяснён. MCP Bundles (`.mcpb`) — zip с локальным сервером и `manifest.json` для установки в один клик, бывшие Desktop Extensions (`.dxt`); их ставит Claude Desktop на macOS и Windows. Это прямая связь с абзацем главы о том, что «установка в один клик — это исполнение кода».

**Что сделать.** Два предложения о публикации и одно о MCPB в тексте или в примечании к графику. Можно добавить полстроки о Server Card WG: будущий `.well-known`-документ, чтобы о сервере можно было судить, не подключаясь к нему (`gaps.md`, строка 369).

**Источник:** registry, quickstart, https://github.com/modelcontextprotocol/registry (docs/modelcontextprotocol-io/quickstart.mdx, проверено 30.09.2026); https://github.com/modelcontextprotocol/mcpb (README, проверено 30.09.2026).

## 11. [minor] FastMCP 4 и сервер без сессий: что ещё тихо перестаёт работать
