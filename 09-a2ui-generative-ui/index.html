A2UI и Generative UI

Агент присылает в чат кнопку «Подтвердить». В ней нет ни строчки JavaScript, только JSON: компонент Button из базового каталога A2UI и действие openUrl с аргументом javascript:alert(document.cookie). Валидатор из официального Python SDK проверяет эту кнопку по каталогу и не находит ошибок, а рендереры на @a2ui/web_core версий 0.9.0–0.10.1 по клику выполняли этот код в origin твоего приложения1. Протокол, который обещает, что агент никогда не присылает код, споткнулся о простую вещь: код всё равно есть, его пишет тот, кто рисует.

Данные, структура или код

Возьми одну задачу. Пользователь пишет агенту «забронируй столик на четверых в пятницу», и в ответ в чате должна появиться форма: дата, время, число гостей, кнопка. Сделать это можно тремя способами, и различаются они не библиотеками, а тем, что именно агент отправляет по сети.

В первом способе модель вызывает инструмент book_table с аргументами {"date": "2026-10-02", "guests": 4}, а фронтенд по имени инструмента выбирает заранее написанный компонент BookingForm и отдаёт ему аргументы как props. По сети едут данные. Код, который рисует, написан тобой до того, как модель что-то сказала, и модель решает только две вещи: какой компонент показать и чем его заполнить. Так устроены типизированные части сообщений tool-${toolName} в Vercel AI SDK2 и хук useFrontendTool в CopilotKit3. CopilotKit называет этот класс controlled.

Во втором способе модель присылает описание интерфейса: плоский список компонентов вида «Column с детьми title, date, submit; DateTimeInput, привязанный к /booking/date». Типы компонентов берутся из каталога, который ты заранее отдал агенту, а рисует их твой рендерер своими нативными виджетами. По сети едет структура. Модель уже решает, из чего собрать экран, но собрать может только из того, что есть в каталоге. Это declarative-класс: A2UI4, json-render от Vercel Labs5, виджеты ChatKit, JSON-дерево, в которое FastMCP сериализует Python-компоненты Prefab. Внутри класса есть второй раскол. Схема бывает фиксированной, когда разметку пишешь ты, а агент подставляет данные, и динамической, когда дерево целиком придумывает модель на каждом ходе. CopilotKit поставляет оба варианта A2UI под этими именами, и выбор между ними сводится к цене: лишний проход генерации по всему дереву на каждом ходе против невозможности показать макет, которого ты не предусмотрел3.

В третьем способе по сети едет код. Сервер или модель присылает HTML с JavaScript, хост запускает его в песочнице — iframe с урезанными правами — и дальше разговаривает с ним сообщениями. В MCP Apps этот HTML заранее написал разработчик MCP-сервера6. В исследовательском Generative UI от Google страницу целиком пишет модель, Gemini 3 с доступом к поиску и генерации картинок7. Между ними гибриды: в FastMCP модель пишет Python-код на Prefab, и он исполняется в Pyodide прямо в браузере8, а режим, который CopilotKit называет Open Generative UI, стримит сгенерированные HTML, CSS и JS в изолированный iframe3. Это open-ended-класс.

Названия у вендоров плывут, поэтому смотреть надо на payload, а не на вывеску. Open Generative UI у CopilotKit в README подключается хуком useComponent, как будто речь о компонентах, но зарегистрированный так widgetRenderer получает строку html3. По payload это open-ended-класс.

Есть архитектура, которая в тройку не ложится. Thesys C1 был OpenAI-совместимым API: ты менял base_url на https://api.thesys.dev/v1/embed и вместо текста получал UI-спецификацию на собственном DSL, которую рисовал компонент <C1Component />9. Генерация интерфейса переезжала внутрь модельного API, а твой бэкенд даже не знал, что отдаёт интерфейс. На сентябрь 2026 года документация C1 помечена как архив, и новым проектам Thesys советует свой следующий продукт, OpenUI9.

Сама идея старая. Server-driven UI, когда бэкенд присылает описание экрана, а нативный клиент его рисует, давно живёт в мобильных приложениях, и в обсуждении запуска A2UI на Hacker News его так и назвали: тот же SDUI, только шаблонизатор теперь модель10. Новое здесь — автор описания. Он ошибается, выдумывает несуществующие компоненты и может выполнять чужие инструкции, пришедшие через промпт-инъекцию.

Сравнивай подходы по одному вопросу: чей код превращает ответ модели в пиксели и кто отвечает, когда модель ошиблась. В controlled ошибка модели — неправильные props у твоего компонента. В declarative — неправильная композиция из правильных деталей. В open-ended — любая страница, и хост гарантирует только прочность клетки.

A2UI изнутри: поверхность, список, данные

Вот та самая форма бронирования в текущей production-версии A2UI, v0.9.1. Поток идёт в формате JSON Lines: каждая строка — отдельное сообщение от агента к рендереру.

Три сообщения — три части любого обмена. createSurface открывает поверхность (surface): область интерфейса со своим деревом компонентов и своей моделью данных, адресуемую по surfaceId. Поверхности не вкладываются друг в друга, и у каждого сообщения v0.9 есть поле version11. updateComponents присылает компоненты, updateDataModel — данные.

В оригинальном примере на странице What is A2UI компонента с "id": "root" нет. А в v0.9 корень задаётся только соглашением: один компонент обязан называться root, отдельного поля для этого нет11. В v0.8 корень указывался явно, полем root в сообщении beginRendering, и при переводе примера на новую версию его потеряли. Схема такую ошибку не ловит, потому что каждый компонент по отдельности валиден, и рендереру просто не с чего начать дерево. В примере выше корень добавлен третьей строкой.

Плоский список вместо дерева

Компоненты лежат не вложенным деревом, а плоским списком. У каждой записи есть id, связи задаются ссылками на чужие id в полях children и child. Это список смежности (adjacency list), и выбран он ради стриминга. Модель генерирует ответ токен за токеном, а вложенный JSON становится валидным только в конце, когда закрыты все скобки. Список самостоятельных записей можно разбирать по мере прихода, но делает это обычно не рендерер: модель пишет один updateComponents со всем массивом, и рендерер получает его целиком. Постепенность даёт потоковый парсер агента. DirectJsonStreamParser из Python SDK достраивает недописанный JSON, шлёт частичные updateComponents с поддеревом, уже достижимым от root, а на место ещё не пришедших детей ставит заглушку, пустой Row12. Поэтому промпт SDK требует от модели писать root первым, а родителей раньше детей. Рендерер буферизует обновления до появления root, а потом рисует то, что есть, пропуская битые ссылки11.

Чтобы поменять один узел, агент присылает ещё один updateComponents с единственной записью под тем же id, не пересылая остальное дерево.

Данные отделены от структуры. {"path": "/booking/date"} вместо строки означает привязку: значение берётся из модели данных поверхности по JSON Pointer (RFC 6901). Агент может обновить данные, не трогая компоненты, и наоборот. В v0.9 у updateDataModel поле path по умолчанию равно /, а сообщение без value удаляет ключ11. В v1.0 это правило перевернули.

Строки можно собирать функцией formatString с интерполяцией ${/user/name} или ${name}, а в v1.0 появилась встроенная @index с номером итерации13. На шаблонах держится экономия: двадцать ресторанов — это один шаблон и один updateDataModel, а не двадцать карточек, которые модель генерирует токен за токеном.

Прежде чем открыть поверхность, агент выбирает каталог. Рендерер в метаданных каждого сообщения передаёт a2uiClientCapabilities со списком supportedCatalogIds, упорядоченным по предпочтению. Агент может заранее объявить свои каталоги в AgentCard. Выбор делается при createSurface и не меняется до конца жизни поверхности, а если общих каталогов нет, агент не присылает интерфейс вовсе14. Совпадение проверяется по строке catalogId.

Что происходит, пока пользователь печатает

Ничего сетевого. Каждое нажатие в TextField синхронно пишет значение в локальную модель данных, и по сети не уходит ни байта. Документация A2UI отдельно подчёркивает следствие: debounce на клиенте не нужен, сеть видит только намеренные действия пользователя14.

Намеренные действия бывают двух видов. Функция (functionCall) выполняется локально в рендерере, например openUrl или проверка формата email, и агенту о ней не сообщают. Событие (event) уходит агенту: у него есть стабильное имя, по которому агент делает switch, и контекст — словарь значений, которые могут ссылаться на модель данных и разрешаются в момент клика.

Агент получает не форму, а только то, что автор кнопки положил в context, уже с подставленными значениями. Отвечает он теми же тремя сообщениями: дополняет компоненты, меняет данные или закрывает поверхность через deleteSurface.

Иногда агенту нужна вся форма без кнопки: пользователь говорит голосом «ну, отправляй». Для этого агент ставит sendDataModel: true в createSurface, и рендерер прикладывает всю модель данных поверхности к каждому исходящему сообщению как метаданные транспорта14. Поверх A2A это выглядит так:

По какому проводу это едет

A2UI не привязан к транспорту. Стабильных привязок две14. Поверх A2A сообщения лежат в DataPart с MIME-типом application/a2ui+json, и поле data может содержать список сообщений, чтобы отправить несколько обновлений за один запрос; список понимает только A2A v1.0 и новее, более ранние версии ждут один объект14. Про сами части сообщений A2A — глава 7. Поверх AG-UI сообщения A2UI транслируются в события AG-UI, этим занимается CopilotKit, автор AG-UI; события разобраны в главе 8. REST, WebSocket и SSE пока в планах, на месте их примеров стоит // TODO: Add an example14.

Третий путь, поверх MCP, описан в отдельном руководстве. Шаблон экрана с привязками и без данных сервер отдаёт как MCP-ресурс под своей схемой URI, например a2ui://recipe-card, с типом application/a2ui+json. Вызов инструмента возвращает только updateDataModel внутри EmbeddedResource плюс текстовый фолбэк, а связь между ними задаётся тем же полем _meta.ui.resourceUri, что и в MCP Apps. Клиент один раз скачивает шаблон и дальше получает только данные15. Каталоги согласуются один раз в initialize или в _meta каждого tools/call. Руководство рекомендует первый, потому что «MCP is a stateful session protocol», но в ревизии MCP 2026-07-28 рукопожатия initialize нет, и новым серверам остаётся второй.

Как агент получает A2UI от модели

Валидатор — последний шаг конвейера, который в SDK 0.7.0 собран почти целиком. DirectJsonFormat строит системный промпт из каталога, модель вставляет интерфейс в теги <a2ui-json> посреди текста, парсер вынимает блоки и чинит висячие запятые и «умные» кавычки12. Повторную генерацию SDK не делает, хотя спецификация её предусматривает: «the errors can be reported back to the LLM in a subsequent prompt, allowing it to self-correct»11.

allowed_components урезает каталог, и валидация идёт по урезанному. С четырьмя компонентами вместо восемнадцати промпт в этом запуске занял 27 тыс. символов против 40 тыс. Ответ без тегов parser.unwrap не пропускает, а бросает A2uiParseError, так что чисто текстовый ответ ловят отдельно. Для ADK вместо тегов есть инструмент SendA2uiToClientToolset. Что лежит в каталоге

Каталог — это документ JSON Schema с полем catalogId, словарём components, где каждому имени компонента сопоставлена схема его свойств, списком функций и, до v1.0, блоком theme. Агент может ссылаться только на компоненты из согласованного каталога, всё остальное — ошибка валидации14.

В базовом каталоге v0.9 и v0.9.1 восемнадцать компонентов (от Text и Button до Modal, Tabs и Video) и четырнадцать функций: логические and, or, not, проверки required, regex, email, length, numeric, форматирование чисел, дат и валют, pluralize и та самая openUrl. Готовый каталог должен быть самодостаточным, без внешних $ref: так его проще целиком положить в промпт модели. Писать его можно модулями, а перед поставкой склеивать отдельным шагом сборки, в примерах проекта это скрипт register-catalogs.js, встроенный в сборку Xcode или Gradle14.

Единого каталога на все клиенты проект не хочет принципиально: «we do not think portability requires a standardized catalog across multiple clients; the LLM can interpret the catalog for each individual frontend»14. Переносимость, по мнению авторов, обеспечит модель, которая прочтёт чужой каталог. На практике это значит, что вывод агента привязан к каталогу конкретного клиента, и «написал один раз, работает везде» получается, только если у клиентов общий каталог, например базовый.

Раз каталог попадает в промпт, он стоит токенов. Для этого в A2UI описаны трансформеры каталога: правило вроде ComponentPruningTransformer вырезает часть компонентов перед тем, как каталог превратится в инструкции для модели, например гостевой режим без полей ввода14. В v1.0 у каталога появилось поле instructions, которое заменило внешний файл rules.txt с правилами дизайна для модели13. Каталог стал одновременно схемой валидации и куском системного промпта, и его размер — вопрос контекст-инженерии из главы 2.

Исправление вошло в @a2ui/web_core 0.10.2: PR #1707, влит 19 июня 2026 года, разрешает только http(s). Advisory опубликовали 3 августа, через шесть недель1. Всё это время тот, кто закрепил версию 0.9.x–0.10.1, был уязвим и не знал об этом. И ещё деталь из проверки 30 сентября 2026 года: глобальная база GitHub Advisory по @a2ui/web_core ничего не возвращала, запись жила только в разделе безопасности репозитория. На npm audit, который опирается на эту базу, здесь рассчитывать не стоит.

В каталоге v1.0 openUrl помечена "requiresUserActivation": true — вызвать её можно только из жеста пользователя, а поле allowedCallers со значением по умолчанию rendererOnly не даёт агенту вызвать функцию напрямую13.

Декларативный протокол не присылает код, но каждая функция каталога — это код, который рендерер выполняет на аргументах, контролируемых агентом. Относись к ним как к публичному API: проверяй схемы URI, длины, диапазоны, и считай агента враждебным.

Так и поступили авторы одного из сторонних рендереров, для Svelte 5. Его модель угроз начинается со слов «assumes a hostile agent»: белый список компонентов, вычистка свойств on* и вызовов функций, отказ от prototype pollution, экранирование текста до разметки, ограничение глубины рекурсии17. README Python SDK предупреждает о том же: фишинг через знакомый интерфейс, скрипты в значениях свойств, раскладки, от которых клиент захлебнётся12. Атаки через интерфейс — в главе 16.

Как каталоги должны меняться и как меняются

Правила эволюции каталога в документации A2UI стоит забрать себе для любой внутренней схемы. Изменения только добавляющие. Устаревшее не удаляется, а помечается deprecated: true с пояснением в x-deprecated-reason. Перечисления считаются открытыми, и неизвестное значение не должно ронять старый рендерер. Неизвестный компонент рисуется безопасной заглушкой, а посредники вроде оркестраторов пересылают незнакомые поля без изменений. Ломающее изменение — только с новой мажорной версией, и номер версии живёт в самом catalogId (…/v1/catalog.json → …/v2/catalog.json), чтобы на время миграции клиент мог объявить оба14.

Сам проект эти правила нарушил примерно через пять месяцев после запуска. В issue #1469 описано, как @a2ui/react 0.10.0 начал отвергать payload v0.8, который принимала 0.8.0: поле MultipleChoice.selections с одновременными path и literalArray. В официальной схеме v0.8 запрета на такое сочетание нет, его добавил новый валидатор рантайма. Issue закрыли со статусом «not planned»18.

Вторая беда тише. Согласование каталога идёт по точному совпадению строки catalogId, а у базового каталога v0.9.1 в разных местах разные строки.

Три поколения за год

В треде запуска A2UI на Hacker News в декабре 2025 года пользователь pscanf написал про всю волну UI-протоколов: «In 6 months time half of them will have been abandoned, and the other half will have morphed into something very different and incompatible»10. Через полгода половина будет брошена, а вторая превратится во что-то совсем другое и несовместимое. Про сам A2UI он угадал вторую половину: протокол жив, но за девять месяцев формат его сообщений менялся дважды. Вот та же форма бронирования в первой публичной версии, v0.8:

Тип компонента здесь ключ объекта-обёртки, строка обёрнута в {"literalString": …}, данные идут массивом пар key/valueString, а корень объявлен в отдельном сообщении. Руководство по переходу на v0.9 объясняет, откуда это взялось и почему от этого отказались. v0.8 проектировали так, чтобы его генерировала модель в режиме structured output, «above all else»: все формы должны были выражаться урезанным подмножеством JSON Schema, которое понимают движки структурированного вывода. v0.9 проектировали так, чтобы его можно было целиком положить в системный промпт. v1.0: кандидат, который продолжает меняться

Каталог specification/v1_0 создан 8 июня 2026 года, в README сказано, что раньше эта версия называлась 0.10. Ярлык release candidate вводит в заблуждение: крупные вещи пришли уже после него. 23 июля «клиент» и «сервер» переименовали в «рендерер» и «агента» по всей спецификации, вплоть до имён файлов схем. 29 июля разрешили смешивать каталоги в одной поверхности, 4 августа появились ограничения allowedParents и корневой компонент Surface, 12 августа — двусторонний RPC и поле userMessage у действий. 29 сентября изменение про зарезервированные ключи с префиксом @ влили и откатили в тот же день20.

Для того, кто будет мигрировать, важны изменения, которые ломают поведение без смены формы сообщений13:

  • В updateDataModel поле value стало обязательным. Удаление ключа теперь "value": null, а сообщение без value — ошибка схемы. В v0.9 то же сообщение удаляло ключ.
  • surfaceId снова обязан быть уникальным за всё время жизни рендерера: v0.9.1 это правило ослабила, v1.0 вернула. Создать поверхность с id, который уже был, без предварительного deleteSurface — ошибка.
  • theme и primaryColor удалены из каталога и из createSurface без замены: оформление целиком принадлежит хосту. Заменявшее их поле surfaceProperties успели добавить в черновик и убрать 31 июля20.
  • createSurface может сразу нести components и dataModel, то есть весь экран одним сообщением.
  • Каталоги v0.9 не работают с рантаймом v1.0 напрямую. functions стал словарём «имя → определение», в метаданных каталога нужен "protocolVersion": "1.0" (без него каталог считается v0.9), имена компонентов и функций обязаны подчиняться правилам идентификаторов Unicode UAX #31.
  • Компонент ищется сначала по своему catalogId, потом по каталогу поверхности, и если не нашёлся, рендерер его не рисует: «There is no fallback to catalogs advertised in capabilities». Смешивать в поверхности можно только каталоги одной версии протокола.

Самая показательная история — с actionResponse. В черновике v1.0 у события кнопки были поля wantResponse и responsePath, а агент отвечал отдельным сообщением actionResponse: синхронный вызов из интерфейса в агента. 27 июля 2026 года issue #2104 предложил заменить эту конструкцию функциями, объявленными в каталоге18, и 12 августа в спецификацию вошли четыре сообщения двустороннего RPC20. Схемы v1.0 сегодня разрешают от агента к рендереру ровно createSurface, updateComponents, updateDataModel, deleteSurface, callRendererFunction и agentFunctionResponse, а в обратную сторону — action, callAgentFunction, rendererFunctionResponse и error16. actionResponse там нет. При этом главная страница документации и обзор концепций до сих пор обещают «client-to-server RPC (actionResponse)»11.

Каждый вызов несёт functionCallId, и ответная сторона обязана скопировать его в ответ. В callRendererFunction поле catalogId обязательно. Ответ содержит либо value, либо error с code и message. Кто может вызывать функцию, в сообщении не пишется: это поле allowedCallers в определении функции в каталоге, со значениями rendererOnly, agentOnly и rendererOrAgent. Рендерер, получивший удалённый вызов функции с rendererOnly или незарегистрированной функции, отвечает ошибкой INVALID_FUNCTION_CALL13.

Рендереры за спецификацией не успевают. У всех поддерживаемых проектом рендереров — React, Lit, Angular, Flutter — v1.0 значится как «🚧 Planned»17. Официальный рендерер для Jetpack Compose от Android (androidx.a2ui) в статусе alpha и поддерживает v0.9.121. Официального SwiftUI-рендерера нет вовсе: в таблице проекта он значится только как «Planned» для v1.0. Стабильный мобильный путь от проекта один — Flutter GenUI SDK, а на iOS без Flutter есть лишь сторонние a2ui-swift и AGenUI с общим ядром на C++ для iOS, Android и HarmonyOS17. Из сторонних v1.0 умеют рендерер для Svelte 5 и uny/a2ui-compose, причём последний только её17.

MCP Apps: HTML в клетке

Вот что сообщает о себе сервер из квикстарта FastMCP 4.0.10, где инструмент возвращает таблицу и круговую диаграмму. Вывод получен запуском, пример сокращён до трёх сотрудников вместо семи.

Весь интерфейс сервер объявил заранее. Инструмент ссылается на ресурс по схеме ui://, ресурс — 471 байт HTML с пустым <div id="root">, скриптом и стилями с jsDelivr. Отсюда домен https://cdn.jsdelivr.net в метаданных ресурса: без него хост не выпустит страницу за скриптом. Результат вызова несёт данные для отрисовки в structuredContent и строку [Rendered Prefab UI] в content. Эту строку и видит модель.

Так работает MCP Apps, расширение MCP с идентификатором io.modelcontextprotocol/ui, описанное в SEP-1865. Ресурс — обычный ресурс MCP с MIME-типом text/html;profile=mcp-app, инструмент ссылается на него полем _meta.ui.resourceUri, хост читает его стандартным resources/read и показывает в песочнице. С песочницей хост разговаривает по JSON-RPC 2.0 поверх postMessage, то есть на диалекте самого MCP: View ведёт себя как MCP-клиент, а хост как сервер, который проксирует настоящий6. Предложение вышло 21 ноября 2025 года, и в коде из того анонса стоял MIME-тип text/html+mcp24; в спецификацию вошёл text/html;profile=mcp-app, и старые примеры с первым вариантом стоит читать с поправкой. 26 января 2026 года спецификация получила статус Stable, и в блоге MCP её назвали готовой к продакшену25. Протокол MCP в целом разобран в главе 5, здесь только то, что добавляет расширение.

Ресурсы объявляются заранее, а не приходят внутри результата, чтобы хост мог скачать шаблон до вызова, закешировать и проверить его до показа. Встраивание HTML прямо в результат, как делал MCP-UI, отложили из-за проверки и производительности. Внешние URL в iframe тоже отложили, «due to concerns around model visibility, inability to screenshot content, and review process»6. Так что утверждение из README CopilotKit, будто с MCP Apps «сервер возвращает URL для iframe»3, неверно: в стабильной спецификации есть только HTML-ресурсы.

Жизненный цикл View

Вызов инструмента и загрузка интерфейса идут параллельно. View первым делом шлёт ui/initialize со своими возможностями: умеет ли он отдавать собственные инструменты, какие режимы показа поддерживает (inline, fullscreen, pip). В ответ хост присылает hostContext: описание вызова, который породил View, тему, CSS-переменные для оформления, режим показа, размеры контейнера, локаль, часовой пояс, платформу. После ui/notifications/initialized хост может досылать аргументы: сначала ноль или больше tool-input-partial, пока модель ещё генерирует вызов, потом ровно один tool-input с полными аргументами, потом tool-result или tool-cancelled6.

Первые грабли автора View — размер. containerDimensions задаётся по каждой оси либо жёстко (height, width), либо потолком (maxHeight, maxWidth). Во втором случае хост «MUST listen for ui/notifications/size-changed», а View на SDK шлёт это уведомление сам через ResizeObserver, если не выключен autoResize. Полноэкранный режим View просит запросом ui/request-display-mode, и хост возвращает режим, который получился на деле, а не тот, что просили6.

Частичные аргументы спецификация описывает честно: это «best-effort recovery of incomplete JSON», хост может закрыть незакрытые скобки и прислать то, что получилось. View такие данные можно показывать, но «MUST NOT rely on partial arguments for critical operations»6. Скелетон карточки из частичных аргументов нарисовать можно, а списать деньги по ним нельзя.

Двойной iframe и CSP

Если хост — веб-страница, между ней и View обязан стоять промежуточный iframe, sandbox proxy. Требования спецификации короткие: у хоста и proxy разные origin, у proxy есть права allow-scripts и allow-same-origin, proxy сообщает о готовности, получает от хоста сырой HTML и загружает его во внутренний iframe с CSP, собранной из метаданных ресурса6. Настольные хосты могут рисовать View напрямую.

Вся конструкция держится на одном правиле: внутренний iframe не получает allow-same-origin. Руководство A2UI, где используется та же схема, объясняет причину: «any iframe with allow-scripts and allow-same-origin can escape its sandbox by programmatically interacting with its parent DOM or removing its own sandbox attribute»26. Шаблон «iframe с sandbox», скопированный из другого проекта, может содержать оба флага: для собственного кода это допустимо, для кода чужого сервера — нет. Цена правила — у View уникальный непрозрачный origin, и в нём нет localStorage, sessionStorage, IndexedDB и cookie. Состояние хранят на сервере или просят у хоста.

Стабильная версия спецификации датирована 26 января, а работа продолжается в черновике29. Самое заметное: инструменты теперь ходят в обе стороны, и хост может вызывать инструменты, которые зарегистрировал сам View. Обоснование в тексте — «Without tool registration, apps are opaque to the model». Там же предупреждение: iframe могут снести в любой момент, поэтому долгую работу View должен отдавать серверу. Черновик добавляет sampling/createMessage из View с требованием к хосту ограничивать частоту, стоимость и спрашивать пользователя, ui/download-file (в песочнице нет allow-downloads, скачать файл напрямую нельзя), ui/notifications/request-teardown для кнопки «Готово» и метаданные _meta.ui прямо в resources/list, чтобы хост мог проверить CSP при подключении. Реализуют ли это ChatGPT и Claude, в открытых источниках на конец сентября 2026 года не видно.

Вокруг расширения поменялся сам MCP: в ревизии 2026-07-28 рукопожатия initialize больше нет30, подробности — в главе 5. Рукопожатие ui/initialize внутри iframe от ядра не зависит, а вот объявление поддержки расширения спецификация по-прежнему показывает через initialize:

Как этот же сигнал передаётся в ревизии без initialize, на 30 сентября 2026 года не описано ни в стабильной спецификации расширения, ни в черновике29, так что не строй логику на единственном способе узнать о поддержке. В дорожной карте MCP от 22 августа интерфейсов среди приоритетов нет31, так что расширение будет развиваться в своём репозитории, а не в ядре.

MCP App на Python за вечер

Писать HTML и мост на postMessage руками не обязательно. Для Python есть FastMCP: интерфейсы в нём появились в версии 3.0.0 (18 февраля 2026), генерация интерфейса моделью — в 3.2.0 (30 марта), текущая версия 4.0.108. Питоновский пакет от авторов MCP-UI, mcp-ui-server, застрял на 1.0.0 от 4 ноября 2025 года32, так что самый короткий путь к MCP Apps на Python сейчас лежит через FastMCP.

  1. Поставь пакет и закрепи Prefab. uv pip install "fastmcp[apps]" "prefab-ui==0.20.2". Prefab — библиотека Python-компонентов от Prefect, на которой FastMCP описывает интерфейсы. FastMCP сам предупреждает, что в Prefab «frequent breaking changes», и задаёт только нижнюю границу версии, так что верхнюю ставь сам.
  2. Напиши инструмент с app=True. Он возвращает не текст, а дерево компонентов.
  3. Запусти fastmcp dev apps server.py. Откроется интерфейс на localhost:8080, сервер поднимется на порту 8000. Выбираешь инструмент, заполняешь аргументы, результат открывается во вкладке внутри того же AppBridge, которым пользуются настоящие хосты. Слева панель инспектора показывает JSON-RPC между браузером и сервером и сообщения postMessage между мостом и View8.

Именно этот сервер выдал JSON из предыдущего раздела. Декоратор с app=True сделал три вещи: зарегистрировал для инструмента ресурс ui://prefab/tool/<hash>/renderer.html с универсальным рендерером Prefab, сгенерировал для него CSP и повесил ссылку на ресурс в _meta.ui. Сам инструмент возвращает JSON-дерево компонентов в structuredContent. Сортировка таблицы, поиск и подсказки на диаграмме работают в браузере, без обращений к серверу.

Подвох для агента: модель получает строку [Rendered Prefab UI], а данные лежат в дереве для рендерера. Если агент должен рассуждать о содержимом таблицы, отдай ему данные отдельным инструментом без интерфейса.

Когда интерфейс зовёт сервер обратно

Форма, которая сохраняет запись, требует серверного инструмента, который модели показывать незачем. Для этого в FastMCP есть FastMCPApp: точки входа регистрируются через @app.ui(), серверные инструменты через @app.tool(), а имя инструмента в кнопке FastMCP разрешает при сериализации, так что монтирование сервера под префиксом её не ломает8.

Сервер отдаёт в tools/list оба инструмента, а дальше работает поле visibility из спецификации MCP Apps. Значение по умолчанию — ["model", "app"]. Хост «MUST NOT include tools in the agent's tool list when their visibility does not include "model"», и хост «MUST reject tools/call requests from apps for tools that don't include "app"». Область "app" ограничена соединением с тем же сервером: вызвать app-инструмент чужого сервера View не может никогда6. Отправка формы в JSON-дереве выглядит как {"action": "toolCall", "tool": "add_note", …}, и модель про add_note не знает вовсе.

Спецификация объясняет, почему это один массив, а не два поля: у OpenAI было widgetAccessible плюс visibility, и одним массивом выражается всё то же самое6. Инструменты, которые нужны только интерфейсу — сохранить, пересчитать, подгрузить страницу, — помечай ["app"]: они не тратят контекст модели и не отвлекают её при выборе инструмента (про цену описаний инструментов — глава 3). Инструмент, который должен срабатывать только от действия в интерфейсе, тоже ["app"]: модель не сможет вызвать его в обход формы.

Когда интерфейс пишет модель

Третий режим FastMCP включается одной строкой, mcp.add_provider(GenerativeUI()). Провайдер регистрирует инструмент generate_prefab_ui, который принимает Python-код, и search_prefab_components, через который модель узнаёт, какие компоненты есть8. Модель пишет код на Prefab с циклами, f-строками и вычислениями, и пользователь видит, как интерфейс собирается по мере генерации.

Iframe рендерера создаётся параллельно с вызовом инструмента, так что к моменту, когда пойдут частичные аргументы, он уже работает. Хост пересылает их через tool-input-partial, рендерер вытаскивает растущую строку code, и Pyodide в браузере исполняет ту часть, которая уже компилируется. Когда модель закончила, сервер прогоняет полный код в серверном Pyodide под Deno, и рендерер заменяет предпросмотр проверенным результатом8. Это буквальное исполнение правила «MUST NOT rely on partial arguments»: частичное — для глаз, итоговое — после проверки. В песочнице только стандартная библиотека и Prefab. Импорт NumPy, pandas или requests даёт ImportError8.

В Claude Code такой интерфейс не нарисуется: это терминал. Документация Claude Code называет UI-ресурсы MCP Apps «pages for a host application to render rather than content for Claude to read», не показывает их в подсказках @ и в списке ресурсов, хотя прочитать ресурс по URI можно33. Модель в терминале получит ту самую строку-заглушку, так что в Claude Code сервер пишут и тестируют, а интерфейс смотрят в fastmcp dev apps или в хосте с поддержкой MCP Apps.

Вечерний план: подними квикстарт, открой инспектор в fastmcp dev apps и найди в трафике ui/initialize, tool-input и tool-result. Потом переделай его в FastMCPApp с формой и проверь в tools/list, что серверный инструмент получил visibility: ["app"]. И добавь рядом обычный инструмент, который возвращает те же данные текстом, чтобы агенту в терминале было что читать.

Разделяй данные и отрисовку

Самый полезный совет из этой документации касается не интерфейса, а проектирования инструментов. «If you attach a widget template to every tool call, ChatGPT can re-render your iframe too often»34. Лекарство — два вида инструментов. Инструменты данных ищут, считают и меняют данные и возвращают только structuredContent. Инструменты отрисовки принимают готовые данные и несут _meta.ui.resourceUri, и только они.

Выигрыш не только в перерисовках. Пример из той же документации: инструмент поиска недвижимости умеет фильтровать по городу, цене и числу спален, но не по школьному округу. Пользователь спрашивает, какие из найденных домов попадают в округ Richmond Primary School. Модель вызывает поиск широко, сама отбирает подходящие варианты и только потом вызывает отрисовку с отфильтрованными id. Виджет появляется один раз, уже с правильным набором. Кнопка «перебросить» в интерфейсе при этом может звать инструмент данных напрямую, не пересоздавая iframe34. Это та же проблема, что и со строкой [Rendered Prefab UI] в FastMCP: модели нужны данные, пользователю — картинка, и смешивать их в одном инструменте неудобно обоим.

Верхний слой совсем свежий. Репозиторий openai/mcp-extensions создан 29 сентября 2026 года, в нём написано «This specification defines extensions to MCP and MCP Apps for use across ChatGPT» и обещана поддержка к запуску на DevDay36. Расширения регистрируют точки входа через _meta["openai/ui"]["entrypoints"]: глобальную в боковой панели, в панели разговора и обработчик файлов по расширению (только в десктопном приложении). При вызове как точка входа _meta["ui"]["visibility"] игнорируется.

У OpenAI есть и собственный декларативный формат, не связанный с MCP Apps: виджеты ChatKit. Корень WidgetRoot (Card, ListView, Form) собирается из узлов Text, Button, Select, DatePicker и других, действия уходят в колбэк onAction на твоём бэкенде, а JSON можно собрать в визуальном Widget Builder37. По идее это каталог, как в A2UI, только один и для одного продукта.

С ним часто путают Open-JSON-UI: CopilotKit описывает его как «An open standardization of OpenAI's internal declarative Generative UI schema», но в документации OpenAI это название не встречается ни разу, собственная страница CopilotKit о нём теперь перенаправляет на страницу про A2UI, а публичной схемы найти не удалось3. Пока это формулировка вендора, а не спецификация.

Разница с A2UI в гранулярности. A2UI обновляет компонент целиком, присылая запись с тем же id, а патч json-render может поменять одно свойство по пути JSON Pointer. Каталоги в формате A2UI json-render рисовать умеет, для этого в документации есть отдельный разбор, но это надстройка, а не родной протокол5. Рендереры у json-render выходят далеко за веб: PDF, письма, видео на Remotion, картинки через Satori.

Формы, подтверждения, потоковая отрисовка

«It seems like latency will be poor if you have to wait for a server-side round trip to an LLM to update the UI whenever you press a button?» — спросил skybrian 17 декабря 2025 года, на второй день треда запуска A2UI10. Если каждое нажатие ждёт ответа модели, интерфейс будет медленным. Он прав для всего, что проходит через модель, и все рабочие паттерны сводятся к тому, чтобы через модель не ходило то, где её решение не нужно.

У каждого подхода для этого есть свой локальный слой. В A2UI это модель данных, которая пишется без сети, функции каталога для форматирования и проверок и поле checks у полей ввода: кнопка, чья проверка не проходит, отключается рендерером до всякого сетевого запроса14. В Prefab это клиентское состояние, SetState и реактивные выражения, а сортировка и поиск в таблице работают в браузере. В MCP Apps это обычный JavaScript во View плюс прямые вызовы инструментов данных, которые хост пересылает серверу без участия модели.

Клик, который уходит агенту, стоит полноценного хода модели. Клик, который вызывает инструмент с visibility: ["app"], стоит одного RPC. Опубликованных замеров задержки для круга A2UI или MCP Apps нет ни у одного вендора, так что это сравнение по устройству, а не по цифрам. Единственная цифра про время из первоисточников — у Google Research: генерация страницы целиком «can often take a minute or two»40.

Протоколы, которые режут поток на самостоятельные единицы, дают промежуточные состояния, которые можно показывать как есть. Протоколы, которые стримят сырые аргументы, дают только предпросмотр, и финальную версию надо перерисовать. В React-рендерере этой заглушкой была отладочная строка [Loading {id}...], и её видели конечные пользователи (issue #2013)18. Заглушка для недостающего узла — часть дизайна, а не отладочный вывод.

Карточки подтверждения

Паттерн «покажи, что агент собирается сделать, и дай нажать да или нет» есть везде, но устроен по-разному. В AI SDK это состояние approval-requested и ответ через addToolApprovalResponse, правила задаются на сервере2. В MCP Apps хост может спросить согласия на ui/message и вообще «MAY decide to block some messages or subject them to further user approval» для всего, что View шлёт серверу6. В A2UI v1.0 у события появилось поле userMessage, человекочитаемое описание того, что сделал пользователь, чтобы в истории чата стояло «подтвердил бронь на пятницу», а не голое confirm_booking16.

Есть и тонкость, о которой спецификации говорят вскользь. Среди остаточных рисков MCP Apps названо «UI can still display misleading content», и единственная защита — хост должен ясно показывать границы песочницы6. Карточка подтверждения, которую нарисовал сам сгенерированный интерфейс, может сказать что угодно. Поэтому подтверждение необратимого действия лучше рисовать силами хоста, из его собственных компонентов, а сгенерированный интерфейс пусть только его запрашивает.

С формами похожая история про данные. В глоссарии A2UI есть понятие NoAI information: данные вроде номера карты, которые не должны попасть в модель ни при какой проводке14. С sendDataModel: true всё, что пользователь ввёл в поверхность, уходит агенту с каждым сообщением, а значит, и в контекст модели. Платёжные поля не место в модели данных сгенерированной формы. Их показывает хост, как requestCheckout в ChatGPT, а сам агентный платёж разобран в главе 10.

Доступность не приходит с каталогом

Issue #1410 в репозитории A2UI открыт 12 мая 2026 года с приоритетом P1 и на 30 сентября не закрыт. Эталонный пример Restaurant Finder генерирует несколько кнопок «Book Now» с одинаковым видимым текстом и разными действиями, что нарушает критерий WCAG 2.4.6: пользователь скринридера не отличит одну от другой18. Предложенные исправления — скрытый текст, aria-label, aria-labelledby — те же, что пришлось бы помнить разработчику, пишущему разметку руками. Декларативный каталог не убирает этот класс ошибок, он переносит его в момент генерации, где за ним следит модель.

Ответ спецификации — в v1.0: атрибуты доступности получили live (off, polite, assertive) и hidden, а нормативный текст требует от каталогов и рендереров передавать эти атрибуты, выводить семантику для скринридера из видимого текста и проверять это линтером SDK13. В MCP Apps доступность целиком на совести HTML сервера, и CopilotKit называет открытый класс тем, где труднее всего гарантировать доступность, фирменный стиль и безопасность3. Есть и обратный взгляд: Бектур Рыскельдиев по итогам шести исследований с незрячими, слабовидящими и пожилыми пользователями маркетплейсов предлагает генерировать адаптированный интерфейс в момент использования41. Его вывод хорошо ложится на каталоги: роль дизайнера смещается «from specifying layouts to specifying policies».

Что делает сервер, а что клиент

Вне зависимости от протокола обязанности делятся одинаково. Сервер или агент отделяет инструменты данных от инструментов отрисовки, проверяет свой вывод по каталогу до отправки и держит у себя источник истины для состояния: iframe могут закрыть в любой момент, а поверхность — удалить. Он же помечает служебные инструменты как ["app"] и кладёт в текстовый результат что-то осмысленное для модели и для хостов без поддержки интерфейсов.

Клиент или хост владеет каталогом и рендерером и проверяет всё повторно, потому что агенту не доверяет. Он держит песочницу и CSP, фильтрует инструменты по visibility, рисует подтверждения опасных действий своими компонентами, вычищает модель данных перед пересылкой сабагентам и решает, что из действий пользователя увидит модель. Если в команде этот список никому не назначен, он не сделан никем.

Выбор для Python-бэкендера на сентябрь 2026 года. Пользователи в Claude или ChatGPT — FastMCP Apps с закреплённым prefab-ui, разделением данных и отрисовки и серверными инструментами с ["app"]. Свой продукт на React с понятным набором экранов — AI SDK 7 с подтверждениями, а декларативный слой добавлять только тогда, когда экраны должен собирать агент. Веб и мобильные клиенты от одного агента — A2UI v0.9.1 со своим каталогом (на iOS пока через Flutter или сторонний рендерер), id с префиксом своего домена и валидацией через a2ui-agent-sdk перед отправкой. Открытую генерацию — только в песочнице и только для того, у чего нет кнопки «отправить». Пересматривать это стоит, когда рендереры A2UI объявят поддержку v1.0 и когда хосты начнут реализовывать черновик MCP Apps с инструментами View и сэмплированием.

Проверь себя

Агент прислал кнопку с openUrl и адресом javascript:…, валидатор по каталогу не нашёл ошибок. Почему валидация не помогла и где должна стоять защита?

JSON Schema проверяет форму: url — строка, и строка на месте. Смысл аргумента проверяет только реализация функции в рендерере. Защита — белый список схем URI в самой функции (так исправлен web_core 0.10.2), плюс в v1.0 requiresUserActivation и allowedCallers в каталоге. Каждую функцию каталога нужно проверять как публичный API, считая агента враждебным.

Почему A2UI передаёт компоненты плоским списком с ссылками по id, а не вложенным деревом?

Из-за стриминга. Вложенный JSON становится валидным только когда закрыты все скобки, а каждая запись плоского списка валидна сама по себе. Разбирает их по мере генерации не рендерер, он получает updateComponents целиком. Это делает потоковый парсер агента: шлёт частичные updateComponents с поддеревом, уже достижимым от root. Рендерер буферизует их до появления root и рисует то, что есть. Поменять один узел — прислать одну запись с тем же id, не пересылая остальное.

Агент и рендерер «поддерживают базовый каталог v0.9.1», ошибок в логах нет, но интерфейс не появляется. Что проверить первым?

Строку catalogId с обеих сторон. Согласование идёт по точному совпадению, а у базового каталога v0.9.1 в разных местах разные строки (v0_9 в файле каталога, v0_9_1 в документации и в хелпере SDK). Если общего каталога нет, агент по протоколу просто не присылает интерфейс, без ошибки.

Пользователь отфильтровал таблицу внутри MCP App и спрашивает агента «что из этого дешевле всего?». Что знает модель?

Ничего о фильтре. Модель видит результат инструмента, а у FastMCP это строка [Rendered Prefab UI]. Действия внутри iframe попадают к модели, только если View отправит ui/update-model-context или ui/message. Отсюда совет отдавать модели данные отдельным инструментом и сообщать об изменениях явно.

Почему sandbox proxy в MCP Apps получает allow-same-origin, а внутренний iframe с кодом сервера — нет?

Proxy живёт на другом origin, чем страница хоста, поэтому allow-same-origin даёт ему доступ только к самому себе. Внутреннему iframe сочетание allow-scripts и allow-same-origin позволило бы добраться до DOM родителя и снять с себя атрибут sandbox. Цена — у View уникальный origin без cookie и localStorage.

Ты переводишь агента с A2UI v0.9 на v1.0 и не меняешь формат сообщений. Что начнёт вести себя иначе?

updateDataModel без value раньше удалял ключ, теперь это ошибка схемы, удаление — "value": null. createSurface с уже использованным surfaceId теперь ошибка: уникальность снова на всё время жизни рендерера. Поле theme исчезло без замены. И каталоги v0.9 с рантаймом v1.0 напрямую не работают.

Зачем разделять инструменты данных и инструменты отрисовки?

Если шаблон висит на каждом вызове, хост перерисовывает iframe слишком часто. Разделение даёт модели сначала получить и отфильтровать данные, а потом один раз вызвать отрисовку с итоговым набором; интерфейс при этом может сам звать инструмент данных, не пересоздавая iframe. Заодно модель получает данные, а не заглушку.

Инструмент save_order должен срабатывать только от кнопки в интерфейсе. Как это выразить и что проверит хост?

_meta.ui.visibility: ["app"]. Хост не включит инструмент в список для модели, а вызов из View пропустит, только если View принадлежит тому же серверу. Модель не сможет вызвать сохранение в обход формы.

Можно ли по tool-input-partial показывать итоговую сумму заказа и по ней же списывать деньги?

Показывать как предпросмотр можно, действовать нельзя. Частичные аргументы — «best-effort» восстановление недописанного JSON с закрытыми хостом скобками, и спецификация прямо запрещает на них полагаться в важных операциях. Действовать только по tool-input и tool-result.

В оркестраторе с несколькими сабагентами поверхности открыты с sendDataModel: true. Что может пойти не так?

a2uiClientDataModel несёт данные всех поверхностей, и без очистки сабагент погоды прочитает форму, открытую банковским агентом. Оркестратор обязан вырезать чужие поверхности перед пересылкой, в Python SDK для этого есть A2uiSubagentMap.strip_unowned_surfaces_from_data_model. Протокол этого не навязывает.

У Google сгенерированные страницы набрали 1736 Эло против 1800 у экспертов. Почему из этого не следует, что открытая генерация готова для продукта?

Сравнивали закешированные результаты, время генерации (минута-другая) не учитывалось, задача была одноходовой, а авторы оценивали собственную систему. На многоходовых правках в EvoGenUI-Bench лучшая модель доводит до конца 37,3% сценариев, и продукт живёт как раз правками.
