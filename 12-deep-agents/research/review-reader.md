## 1. [CRITICAL] Подсвеченные строки кода (`data-hl`) рендерятся с невидимым текстом — ключевой пример главы выглядит сломанным

**Место:** раздел `#build` («Свой deep agent за вечер»), блоки `data-title="Набросок: mini_agent.py, часть 1"` (`data-hl="8-10,22-25"`) и «часть 2» (`data-hl="12-13,24-25,33-38"`); а также раздел `#subagents` → «Четыре ступени оркестрации», блок `data-title="Сохранённый workflow (из документации)"` (`data-hl="5,8-10"`).

**Доказательство:** скриншот `_qa/12-deep-agents-reader/sec-11.png` и увеличенные кропы `crop2.png`, `crop3.png` (mini_agent.py) плюс отдельный прямой рендер `sec-04-full.png` → `sec04-jscode.png` (workflow-пример), снятые headless Chrome напрямую (`?qa=1&only=sec:N`), помимо стандартного прогона `qa.mjs`.

В исходнике строка 8–10 части 1 — это
```python
INLINE_LIMIT = 4000                      # символов результата, которые идут в окно целиком
VERIFY = "python -m pytest -q"           # внешняя проверка «готово»
DENY = ("rm -rf", "git push", "sudo ", "curl ", "wget ")
```
На скриншоте эти три строки (они входят в подсвеченный `data-hl`-диапазон) отрисованы так:
```
                4000                      # символов результата, которые идут в окно ц
                "python -m pytest -q"           # внешняя проверка «готово»
                "rm -rf"  "git push"  "sudo "  "curl "  "wget "
```
`INLINE_LIMIT =`, `VERIFY =`, `DENY = (` полностью исчезли — видны только строковые литералы, число и комментарий. То же в строках 22–25 части 1: вместо `{"name": "task", "description": "Give a read-only investigation to a subagent…"}` и `SUB_TOOLS = [t for t in TOOLS if t["name"] in ("read_file", "bash")]` видно `"name"  "task"  "description"  "Give a read-only…` и `for   in   if   "name" in "read_file" "bash"` — фигурные скобки, двоеточия, имена переменных `t`, `TOOLS`, `SUB_TOOLS` пропали. В части 2 то же самое на строках 12–13, 24–25, 33–38 (`if not read_only and checks > 0` превращается в `if not      and     0`). В JS-примере workflow (`data-hl="5,8-10"`) `const found = await agent(...)` превращается в `const        await agent 'List every…'`.

Не подсвеченные строки того же блока (например `READ_ONLY_CMDS = {...}`, `def permitted(...)`) отрисованы нормально — проблема именно в стилях подсветки строки (`data-hl`), а не в самой подсветке синтаксиса. В YAML-блоке `.claude/agents/code-reviewer.md` (раздел `#subagents`, `data-hl="4,6"`) та же механика подсветки строки работает исправно — `tools: Read, Glob, Grep` и `permissionMode: acceptEdits` полностью читаемы (см. `crop_yaml3.png`). То есть баг воспроизводится в Python и JavaScript, но не в YAML — похоже на то, что в подсвеченной строке пропадает какой-то класс токенов hljs (пунктуация/операторы/голые идентификаторы), характерный для этих языков.

**Проблема:** это не оговорка вёрстки, а сломанный пример в разделе, который прямо учит писать харнесс с нуля — именно там, где текст говорит «каждая деталь здесь — уменьшенная копия чего-то из этой главы» (строка 835) и просит читателя разобрать код построчно. Читатель, дошедший до этого места, увидит код, который выглядит синтаксически неполным, и не поймёт, обман ли это вёрстки или у автора ошибка в примере.

**Что сделать:** править не текст главы (разметка `data-hl` в HTML корректна и соответствует AUTHORING.md), а общий стиль подсветки строк в `assets/book.css`/`book.js` (или конфигурацию highlight.js), который, судя по всему, делает текст «неглавных» токенов в подсвеченной строке прозрачным/сливающимся с фоном для python/javascript-грамматик, но не для yaml. До фикса — не использовать `data-hl` на строках с голыми идентификаторами и пунктуацией в python/js-блоках этой и, вероятно, других глав (проблема на уровне общего ассета, не только 12-й главы).

## 2. [MAJOR] «auto mode» используется до своего определения — реальный обрыв нити

**Место:** раздел `#subagents` («Сабагент — способ выбросить контекст»), абзац про инъекции: «Итоговое сообщение сабагента родитель читает как результат инструмента… **В auto mode** к этому добавляются классификаторы на передаче задачи (могут запретить) и на возврате результата (только предупреждают)».

Термин `<dfn>auto mode</dfn>` формально вводится и объясняется только пятью подразделами позже, в разделе `#permissions` («Кто нажимает «да»»): «Ответом стал **auto mode**, в котором решение принимает классификатор» — и дальше на полторы страницы разбирается трёхуровневый конвейер, две стадии классификатора, что он видит и не видит.

**Проблема:** это ровно «термин раньше определения» — при первом чтении в разделе про сабагентов у читателя ещё нет модели того, что такое auto mode (что решения принимает LLM-классификатор, а не человек), а текст уже опирается на эту модель («классификаторы на передаче задачи… могут запретить»). Целевой читатель, скорее всего, знает Claude Code в быту, но именно эта глава подробно объясняет механику auto mode как новое знание — то есть текст сам относится к термину как к тому, что нужно объяснять, просто объясняет его слишком поздно.

**Что сделать:** либо дать при первом упоминании (в разделе `#subagents`) короткую вставку-отсылку («…в auto mode — режиме, где решение об одобрении вызова принимает классификатор, а не человек, разбор в разделе 12.7…»), либо переставить абзац про сканирование инъекций и классификаторы на передаче/возврате результата в раздел `#permissions`, где уже введён термин.

## 3. [MAJOR] Для второй схемы Anthropic (планировщик/исполнитель/оценщик) нет рисунка — механизм собирается из абзацев

**Место:** раздел `#long-running` («Агент на много окон»), подраздел «Планировщик, исполнитель, оценщик»: «…ролей стало три. Планировщик превращает одно-четыре предложения в спецификацию продукта… Исполнитель работает спринтами. Оценщик кликает по приложению через Playwright MCP и выставляет оценки с жёсткими порогами по каждому критерию. Перед каждым спринтом исполнитель и оценщик через файлы договариваются о контракте спринта… С выходом Opus 4.6 харнесс начали упрощать… Спринты ушли, оценщик стал делать один проход в конце».

**Проблема:** это ровно тот случай, который AUTHORING.md §6 называет условием для рисунка — «кто кому что отправляет, через какие состояния проходит задача» (три роли, обмен файлом-контрактом, эволюция схемы во времени с конкретными числами по стоимости). Соседняя, более простая двухролевая схема (инициализатор → кодер, ноябрь 2025) получила свой флоучарт `fig-initializer`; более сложная и более длинная по тексту трёхролевая схема (март 2026, с изменением во времени после Opus 4.6) — нет, хотя `research/gaps.md` (раздел «Diagram candidates», пункт 5) прямо предлагает такую схему: «Planner / generator / evaluator with a sprint contract… Annotate "removed on Opus 4.6: sprints; evaluator → single pass"». Заметки главы сами отметили эту возможность, но в готовый текст она не попала.

**Что сделать:** добавить `<figure class="fig" id="fig-planner-generator-evaluator">` (mermaid `flowchart` или `sequenceDiagram`, до 14 узлов) с тремя ролями, файловым «контрактом спринта» между исполнителем и оценщиком и пометкой, что после Opus 4.6 спринты и повторные проходы оценщика убрали — по образцу уже готового наброска в `gaps.md`.
